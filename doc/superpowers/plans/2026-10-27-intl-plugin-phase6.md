# Intl Plugin Phase 6 (Packaging) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and ship the plugin beyond the Linux and single-architecture macOS host:
- Android: `libhermesintl.so` for arm64-v8a, armeabi-v7a, x86 and x86_64, linked against `libjsi.so`, in the Hermes Android build and AAR, verified on the emulator (smoke test and the whole plugin-mode test262 set);
- Apple: `hermesintl.framework` for every slice Hermes builds (macOS, iOS, iOS simulator, Mac Catalyst, tvOS, tvOS simulator, visionOS, visionOS simulator), linked against `hermesvm.framework`, in `hermesintl.xcframework`, the `hermes-ios` tarball and the podspec, verified on the Mac (link checks, the iOS simulator, Catalyst and macOS runs, universal macOS `check-intl`);
- Windows: `hermesintl.dll` for x64 and arm64, built with a Windows loader and default detection, cross-built on this Linux host with clang-cl and the MSVC SDK, and tested under Wine; native verification waits for a Windows agent (user decision);
- one generic CMake mechanism that runs cargo for the target triple of any of these builds, multi-configuration generators included.

Emscripten is not in this phase (user decision): the loader keeps loading no libraries there, and the spec says so permanently.

**Architecture:**
- CMake maps the build (Android ABI, Apple platform × architectures, Windows processor, or the host) to Rust target triples, runs `cargo build --target` per triple (combining Apple architectures with `lipo`), and links the right native libraries per target. Cross builds need `IMPORT_HOST_COMPILERS` for the bytecode.
- The plugin links its platform's JSI provider: `libjsi.so` on Android, `hermesvm.framework` on Apple target platforms, its own static copy of JSI on Windows (MSVC matches C++ types by name across DLLs). Plain Linux and macOS host builds keep `-undefined dynamic_lookup`.
- The loader gains an Apple sibling-framework candidate, treats an Apple "incompatible architecture" failure as no plugin, drops the search-path step on C libraries whose messages it does not know, and gains a Win32 implementation.

**Tech Stack:** CMake 3.21+, cargo/rustup (targets per platform, Rust ≥ 1.95 for tvOS and visionOS), Android NDK (r27/r28) and AGP, Xcode and `xcodebuild -create-xcframework` (on the Mac agent), clang-cl + lld-link + xwin's MSVC CRT/SDK + Wine 9 (on this host), ICU4X 2.3 (`icu::time::zone::WindowsParser` for Windows zones).

## Planning decisions

Task 8 writes these into the spec.

1. **One cargo mechanism for every target.** `cmake/modules/HermesIntl.cmake` gets `hermes_intl_rust_targets(<out-triples> <out-env-var> <out-reason>)`, a pure function (testable with `cmake -P`) that maps the build to Rust triples:
   - a cache variable `HERMES_INTL_RUST_TARGET` (a list) wins;
   - not cross-compiling and no Apple target platform: the host triple from `cargo -vV`, or, on macOS, `{aarch64,x86_64}-apple-darwin` per entry of `CMAKE_OSX_ARCHITECTURES` (empty: the host architecture);
   - Android (`ANDROID_ABI`): arm64-v8a `aarch64-linux-android`, armeabi-v7a `armv7-linux-androideabi`, x86 `i686-linux-android`, x86_64 `x86_64-linux-android`;
   - Apple (`HERMES_APPLE_TARGET_PLATFORM` × architectures): macosx `{aarch64,x86_64}-apple-darwin`; iphoneos `aarch64-apple-ios`; iphonesimulator `aarch64-apple-ios-sim`/`x86_64-apple-ios`; catalyst `{aarch64,x86_64}-apple-ios-macabi`; appletvos `aarch64-apple-tvos`; appletvsimulator `aarch64-apple-tvos-sim` only; xros `aarch64-apple-visionos`; xrsimulator `aarch64-apple-visionos-sim` only (decision 5); deployment variables `MACOSX_DEPLOYMENT_TARGET`, `IPHONEOS_DEPLOYMENT_TARGET` (iOS, its simulator and Catalyst), `TVOS_DEPLOYMENT_TARGET`, `XROS_DEPLOYMENT_TARGET`, from `CMAKE_OSX_DEPLOYMENT_TARGET` when it is set;
   - Windows (`CMAKE_SYSTEM_PROCESSOR`, `CMAKE_VS_PLATFORM_NAME` or `CMAKE_CXX_COMPILER_ARCHITECTURE_ID`): x64/AMD64 `x86_64-pc-windows-msvc`, ARM64 `aarch64-pc-windows-msvc`;
   - Emscripten: a permanent reason ("the plugin is not built for Emscripten; embedders can register a plugin with registerIntlPlugin");
   - any other cross build: a reason naming `HERMES_INTL_RUST_TARGET`.

   `intl/CMakeLists.txt` runs `cargo build --locked --lib [--release] --target <t>` once per triple (separate commands: the build script writes the cbindgen header, so only the first gets `HERMES_INTL_CORE_HEADER`), imports `<cargo>/<t>/<profile>/<lib>`, and with two Apple triples runs `lipo -create` into `<cargo>/universal/<profile>/`. At configure time each triple's std must be installed (`<rustc --print sysroot>/lib/rustlib/<t>/lib` exists), else a configure error naming `rustup target add <t>`; the minimum Rust version becomes 1.95 when a tvOS or visionOS triple is selected. Native libraries per target replace today's list: linux-gnu `Threads dl m`, android `dl log m`, Apple none beyond the system (plus CoreFoundation for `Defaults.cpp`), windows-msvc `kernel32 ntdll userenv ws2_32 dbghelp`. A cross build with `HERMES_BUILD_INTL` on and no `IMPORT_HOST_COMPILERS` is a configure error. The plugin's bytecode step names the hermesc target (`$<TARGET_FILE:hermesc>`) or the imported one, so the suffix and per-config directory are right.
2. **Multi-configuration generators are supported** (Visual Studio is what Windows CI uses): the cargo profile and output path come from `$<CONFIG>` generator expressions (Debug → dev profile, every other configuration → `--release`), with `IMPORTED_LOCATION_<CONFIG>`; `check-intl-rust` does the same.
3. **Defaults** (user decision for mobile): `HERMES_BUILD_INTL` defaults to ON for Linux and macOS hosts (universal macOS included), Android and every Apple target platform; OFF for Windows until the Windows agent verifies a native build (flipping it then also needs the CI and test prerequisites Task 7's checklist lists); unsupported for Emscripten. The host-`hermesc` stages of the Android and Apple builds stay `-DHERMES_BUILD_INTL=OFF`.
4. **JSI providers.** Android links the CMake `jsi` target (`libjsi.so`, `NEEDED libjsi.so`) with `-Wl,--no-undefined`, and configure fails if `HERMES_BUILD_SHARED_JSI` is off (a static JSI would be a second copy). The condition is CMake's `ANDROID` (set by the NDK toolchain), not `HERMES_IS_ANDROID`. Apple framework builds (`HERMES_BUILD_APPLE_FRAMEWORK` on) link `hermesvm` (the framework, which does not pass JSI on) instead of `-undefined dynamic_lookup`, with `LC_RPATH` `@loader_path/..` (shallow bundle) or `@loader_path/../../..` (deep bundle). Windows links the static `jsi` target into the DLL: the binary contract's "never contains its own copy" becomes "except on Windows, where each module has its own copy and MSVC's runtime matches types by decorated name"; a probe on the Windows agent must confirm it (until then it is recorded as unverified). Linux and macOS host builds, and non-framework Apple builds (the simulator test262 route of decision 11), keep `-undefined dynamic_lookup` and bind to the executable that exports the VM.
5. **Apple slices and the loader** (user decision): the tvOS and visionOS simulator slices of the plugin are arm64 only (Rust has no supported x86_64 target there), so `hermesintl` gets `OSX_ARCHITECTURES arm64` in those builds while hermesvm keeps `x86_64;arm64`. On Apple platforms only, the loader treats a `dlopen` failure whose message reports an incompatible architecture ("incompatible architecture" in dyld's text) as **no plugin**, silently, like an absent file. Every other failure stays fatal.
6. **Apple packaging.** `hermesintl` becomes a framework when `HERMES_BUILD_APPLE_FRAMEWORK` is on, with the same properties as hermesvm through a helper moved out of `lib/CMakeLists.txt` into `cmake/modules/Hermes.cmake`, and its own bundle identifier `dev.hermesengine.intl.<platform>`. The loader gains one Apple-only default candidate after the existing ones: when the Hermes image's directory is `<p>/<name>.framework` (shallow) or `<p>/<name>.framework/Versions/<v>` (deep), the candidate is `<p>/hermesintl.framework/hermesintl` (a pure function, unit-tested on Linux). `utils/build-apple-framework.sh` builds `hermesvm hermesintl` per slice, copies and dSYMs both, and makes `universal/hermesintl.xcframework`; `hermes-engine.podspec` always vendors both xcframeworks, but the plugin must be a **weak, non-required** dependency of the app: CocoaPods links vendored frameworks, and a required link would make an app without a matching plugin slice (the x86_64 tvOS/visionOS simulators, decision 5) or with the plugin removed fail to launch. The podspec adds `-weak_framework hermesintl` for consumers (or another mechanism the Mac shows to work), and Task 5 verifies it with a real CocoaPods consumer app: it launches and has `Intl` from the plugin, still launches with `hermesintl.framework` deleted from the built app (no plugin), and an x86_64 tvOS simulator build of it launches without the plugin. If no mechanism makes the dependency weak, Task 5 stops and reports, since decision 5 depends on it; the CI workflows install Rust and the slice's targets, check the plugin framework and its dSYM, and `validateHermesFrameworksExist` requires `hermesintl.xcframework`. React Native's own podspec (another repository) needs a matching change, which Task 8 records in the spec.
7. **Android packaging.** `android/build.gradle.kts` adds `hermesintl` to the native targets and passes `-DHERMES_BUILD_INTL=ON`; nothing else is needed for the AAR (the `.so` lands in `jni/<abi>/`). The CI workflows that build the AAR install rustup and the four targets. The loader needs no Android change (default resolution finds the plugin next to `libhermesvm.so`, or through the search path when libraries are mapped from the APK). A runner option or wrapper runs plugin-mode test262 on a device through `adb` (decision 11).
8. **Windows.** The loader gets a `_WIN32` implementation: the Hermes module's directory from `GetModuleHandleExW(FROM_ADDRESS | UNCHANGED_REFCOUNT, &installIntlPlugin)` + `GetModuleFileNameW` (growing buffer); candidates next to it, then `..\lib` when the directory is named `bin` (case-insensitive); `LoadLibraryExW(path, nullptr, LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS)`; `fileAbsent` from `GetFileAttributesW`; `GetProcAddress`; messages from `FormatMessageW` with the error code; paths UTF-8 in, UTF-16 to Win32 (`MB_ERR_INVALID_CHARS`; invalid UTF-8 is fatal); `IntlPluginPath` with a separator goes through `GetFullPathNameW`, a bare name loads with `LOAD_LIBRARY_SEARCH_DEFAULT_DIRS` (never the current directory). No search-path step and no promotion on Windows. The DLL exports only `hermes_intl_get_entry` (`__declspec(dllexport)` through a macro in `Plugin.cpp`), lands in the tools' runtime directory (`RUNTIME_OUTPUT_DIRECTORY`), links `/OPT:REF` even in Debug, and the build requires a shared CRT (`/MD` or `/MDd`; a static CRT is a configure error). The DLL is also copied next to `hermesvm.dll` after the build (a shared-library host such as `hermes-jsi-shared` resolves from `hermesvm.dll`'s directory), and its runtime directory follows `add_hermes_tool`'s handling of `CMAKE_CFG_INTDIR`. Because `std::string` and `std::vector` cross the interface, `hermes_intl_entry::flags` records, on MSVC, the exact `_ITERATOR_DEBUG_LEVEL` (0, 1 or 2, two bits) and whether the debug CRT is used (`_DEBUG` with `_DLL`, one bit); the loader rejects any difference with a message naming both values, and `HERMES_INTL_PLUGIN_INTERFACE_VERSION` becomes 2. Elsewhere the bits are 0.
   Defaults: the locale from `GetUserDefaultLocaleName` through `core::localeFromHost`; the time zone from `GetDynamicTimeZoneInformation().TimeZoneKeyName` mapped by a new Rust function `host::time_zone_from_windows(id, region)` over ICU4X's `WindowsParser` (CLDR windowsZones, no new data file) and turned into the primary IANA identifier, with the region from `GetUserDefaultGeoName` when available and a retry with `001` when that region has no row for the zone (`parse(id, region).or_else(|| parse(id, None))`; ICU4X looks up the exact pair), else `001`. `TZ` is not consulted on Windows (the CRT's own `TZ` format is not IANA); the spec states that `Date` and `Intl` may then disagree when a user sets `TZ`.
   Tests on this host: the Rust function with `cargo test`; the whole Windows build cross-compiled with clang-cl, lld-link and xwin's CRT/SDK through a committed toolchain file; `hermes.exe`, `hermes-jsi-shared.exe` with `hermesvm.dll`, and `hermesintl.dll` run under Wine (default resolution for both hosts, `IntlPluginPath`, the error cases, a Release-linked fixture DLL whose entry carries a different ABI-bit pattern rejected before any call into it (a real Debug plugin cannot load under Wine, which has no debug CRT DLLs; the real Debug/Release pairing is on the Windows-agent checklist), `Intl` working, defaults from Wine's locale and zone), Release builds only (Debug builds are compiled and linked, since the debug CRT DLLs are not redistributable), and plugin-mode test262 under Wine if it runs in reasonable time. The Windows CI workflow is unchanged until the Windows agent verifies a native build.
9. **The fail-open search path.** On C libraries whose `dlopen` message the loader does not recognise (anything other than glibc, musl and bionic), the search-path step is compiled out, as on Apple: default resolution is registration, next to Hermes, then `../lib`. Windows has no search-path step either (decision 8). The spec's Risks item becomes a statement of the rule.
10. **Two Hermes fixes the packaging needs.** (a) The CLI does not compile in mobile builds: `cli::withIntlPluginFlags` is declared inside `#ifndef HERMES_IS_MOBILE_BUILD` (`include/hermes/VM/RuntimeFlags.h`) and defined inside the same guard in `lib/VM/RuntimeFlags.cpp`, but called unconditionally from `tools/hermes/hermes.cpp` and `tools/hvm/hvm.cpp`; both the declaration and the definition move out of the mobile-only exclusion. Phase 0 introduced it; fix it so the tools build with `HERMES_IS_MOBILE_BUILD` on (its own commit, which the squash folds into Phase 0). (b) On Android every tool without a JVM dies at exit: `makeDefaultFinalizerThreadRunner()` (`API/hermes/hermes.cpp`) wraps the finalizer thread in `facebook::jni::ThreadScope`, which aborts when fbjni has no JavaVM. The fix: the command-line tools pass a plain `ThreadRunner` (a thread with no JNI attachment) through `RuntimeConfig` on Android, and `makeWorkerRuntimeConfig` (`API/hermes/IntlPluginLoader.cpp`, called from `API/hermes/extensions/Worker.cpp`) carries the parent's finalizer runner into Worker runtimes (the parent runtime's record keeps the runner it was created with, so the function can copy it), so a Worker created by a tool does not fall back to the JNI runner. This bug predates the branch (also on `static_h`), so it stays its own commit through the squash.
11. **Mobile tests.**
    - Android, on this host: the x86_64 emulator (`sg kvm -c "emulator -avd <avd> -no-window -read-only -no-snapshot"`; the only image is Android 36 `google_apis` x86_64, whose native bridge runs arm64 executables).
