# JS Parser — Phase P5 (Flow type grammar + declarative integration) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) tracking. The C++ in `lib/Parser/JSParserImpl-flow.cpp` (and the Flow call sites in `JSParserImpl.cpp`) IS the spec — port it faithfully from the cited line ranges; the byte-for-byte `parser_differential` vs `hermesc -dump-ast -parse-flow` is the gate.

**Goal:** Port the Flow **type-annotation grammar** (the whole `parseTypeAnnotationFlow` hierarchy: conditional / union / intersection / prefix / postfix / primary, function types, object types, tuple types, generics, type-args, type-params, predicates, variance), the **declarative type surface** (`type` aliases incl. `opaque type`, `interface` declarations), and the **non-ambiguous integration** that hangs annotations off already-ported productions (function/method type-params + return types + predicate, the leading `this` param, binding/array/object-pattern annotations, class type-params + `extends` super-type-args + `implements` + field types + member variance). After P5, Flow programs whose type usage does not require expression-level backtracking dump byte-identically to `hermesc -dump-ast -parse-flow`.

**Explicitly DEFERRED to P6 (Flow phase 2)** — the *ambiguous expression-level* Flow features that need `SavePoint` + message-suppression backtracking, plus the Flow runtime extensions: typed arrows (return type/predicate/type-param backtracking), `as`/`as const`, type-cast `(x: T)` / `CoverTypedIdentifier`, call/new type-args `f<T>()` / `new C<T>()` / `?.<T>()`, `declare` statements (function/hook/module/namespace/class/variable/export), `enum`, `component`/`hook` syntax, `match`, `record`, and `import type`/`export type`. Each P5 omission site gets a `// P6` comment + an honest error where reachable.

**Architecture:** The type grammar is a large new sibling module `rust/crates/parser/src/js/flow.rs` (mirrors C++ `JSParserImpl-flow.cpp`; `impl<'gc,'ast,'ctx,'a> JSParserImpl<...>` block, `mod flow;` in `js/mod.rs`). Reachability for the differential grows through a top-level `type`/`interface`/`opaque type` declaration (routed from `parse_declaration` via a new `parse_flow_declaration`, gated by a new `Context::parse_flow` flag) — exactly how P1 grew the expression grammar through expression-statements. Integration sites in `functions.rs`/`statements.rs`/`classes.rs`/`expressions.rs` replace their `// P6/P7` stubs with real `parse_type_annotation` / `parse_type_params_flow` / `parse_type_args_flow` calls, gated by `self.parse_types()`.

**Tech Stack:** the `ast` + `parser` crates; `hermesc` (`cmake-build-asan/bin/hermesc`) as the differential oracle, now invoked with `-parse-flow`.

**Spec:** `doc/superpowers/specs/2026-06-06-js-parser-design.md`. **Builds on P0–P4** (`plans/2026-06-06…p0/p1/p2`, `plans/2026-06-07…p3`, `plans/2026-06-08…p4`).
