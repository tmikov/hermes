Found 2026-09-14 by an external review of the `try`-with-result fix
(commit "Wasm: a `try` with a result type whose body falls through now
compiles"), and verified against the compiler.

`onEnd` has three copies of the same loop -- for Try
(`WasmIRGen.cpp:4241`), Block/If (`:4306`) and Loop (`:4368`) -- that run
when the construct was entered in unreachable code:

    for (auto t : entry.resultTypes) {
      if (t == WasmValType::I64) {
        push(builder_.getLiteralUndefined());
        push(builder_.getLiteralUndefined());
        valueStackIsI64Hi_.back() = true;
      } else {
        push(builder_.getLiteralUndefined());
      }
    }

`unreachable_` is true on every one of these paths, and `push()` is a
no-op while it is (`WasmIRGen.cpp:6275`). So the two pushes do nothing
and `valueStackIsI64Hi_.back()` reads a vector that the resize above
just truncated. On an empty stack that is a null dereference; on a
non-empty one it marks a slot belonging to the ENCLOSING block as an
i64 high word, which is silently wrong rather than fatal.

Reproduces on valid Wasm:

    (module (func (export "p") (result i32)
      (unreachable)
      (try (result i64) (do (unreachable)) (catch_all (unreachable)))
      (drop)
      (i32.const 1)))

    AddressSanitizer: SEGV WasmIRGen.cpp:4245:37 in WasmIRGen::onEnd()

The fix is to mark the slot only when the push actually happened, in all
three copies -- or, better, to give them one helper, since they are
character-for-character identical.
