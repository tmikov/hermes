Found 2026-09-14 by an external review of the `try`-with-result fix
(commit "Wasm: a `try` with a result type whose body falls through now
compiles"), and verified against the compiler.

`onEnd` has three copies of the same loop -- for Try
(`WasmIRGen.cpp:4241`), Block/If (`:4306`) and Loop (`:4368`) -- that run
when the construct was entered in unreachable code:

    for (auto t : entry.resultTypes) {
      if (t == WasmValType::I64) {
        push(builder_.getLiteralUndefined());
        push(builder_.getLiteralUndefined());
        valueStackIsI64Hi_.back() = true;
      } else {
        push(builder_.getLiteralUndefined());
      }
    }

`unreachable_` is true on every one of these paths, and `push()` is a
no-op while it is (`WasmIRGen.cpp:6275`). So the two pushes do nothing
and `valueStackIsI64Hi_.back()` reads a vector that the resize above
just truncated. On an empty stack that is a null dereference; on a
non-empty one it marks a slot belonging to the ENCLOSING block as an
i64 high word, which is silently wrong rather than fatal.

Reproduces on valid Wasm:

    (module (func (export "p") (result i32)
      (unreachable)
      (try (result i64) (do (unreachable)) (catch_all (unreachable)))
      (drop)
      (i32.const 1)))

    AddressSanitizer: SEGV WasmIRGen.cpp:4245:37 in WasmIRGen::onEnd()

The fix is to mark the slot only when the push actually happened, in all
three copies -- or, better, to give them one helper, since they are
character-for-character identical.

    Two corrections to the closing note above, from the review of the fix.

    "A mixed `(result i32 i64)` list where the mark has to land on the
    second slot of the pair" was wrong twice over: nothing is pushed on that
    path at all, and in `(i32 i64)` the high half would be the top slot
    anyway. mixedI64 is the Block case again for this defect; it is kept for
    the multi-type signature decoding, and the comment now says so.

    "back() is a null dereference" was also wrong. std::vector<bool> can
    keep its storage after shrinking, so the empty-vector access is
    undefined behaviour that ASan actually reported as a
    heap-buffer-overflow, which is what the commit's own output shows.

    Two reachable cases were added, since every case above runs with
    unreachable_ set and so says nothing about where the marker goes when it
    goes anywhere:

      - liveMixed: a `(result i64 i32)` block, so the high half is not the
        top slot when the results are consumed. Dropping pushI64's marker
        makes it fail with "expected i64 hi32 on top of stack".
      - ifParam: an `if` with an i64 param whose then arm ends in `return`,
        so onElse re-pushes the saved param with unreachable_ still set from
        that arm. It passes only because onElse resets unreachable_ BEFORE
        the re-push; moving the reset after it makes the case fail with a
        heap-buffer-overflow. Nothing had covered that ordering.
