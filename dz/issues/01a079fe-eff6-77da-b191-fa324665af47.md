Found 2026-09-07 by external review of `01a079c6-fdd6`, then measured.

An i64 global whose initializer is an EXTENDED CONSTANT EXPRESSION is
initialized to the last constant the expression mentions, not to the value of
the expression. The module is valid, nothing is diagnosed, and the wrong
number is simply used.

## Reproducer

```wat
(module (global (export "g") i64 (i64.add (i64.const 1) (i64.const 2))))
```

```
                                        Hermes    Node v24.13.1
(i32.add (i32.const 1) (i32.const 2))      3        3     <- i32 is CORRECT
(i64.add (i64.const 1) (i64.const 2))      2        3
(i64.mul (i64.const 3) (i64.const 5))      5       15
```

Bytes for the i64 add case:
`0,97,115,109,1,0,0,0,6,9,1,126,0,66,1,66,2,124,11,7,5,1,1,103,3,0`

`WebAssembly.validate` returns true in both engines; extended constants are
enabled for validation at `WasmCompile.cpp:173`, and wabt's validator permits
i64 arithmetic in a constant expression.

## Mechanism

`WasmGlobal` carries both a scalar `initKind`/`initValue` pair and an
`initExpr` vector, and `initializeGlobals()` prefers the vector only when
`initExpr.size() > 1` (`WasmIRGen.cpp:7628-7640`). The reader populates
`initExpr` for the i32 forms (`BinaryReaderHermesIRGen.cpp:584-598`) and for
`global.get` regardless of type (693-701), but NOT for i64 constants or i64
arithmetic. An i64 extended constant therefore leaves `initExpr` with fewer
than two entries and falls back to the scalar pair -- which each i64 constant
overwrote in turn, so it holds the last one.

The comment on `initExpr` already says "Only i32 globals can currently
produce one" (`WasmTypes.h`), so the gap is known; what is missing is that the
fallback is silently WRONG rather than diagnosed.

## Scope

i32 is correct, including through the optimizer. f32/f64 cannot reach this:
the extended-const proposal admits only i32/i64 `add`/`sub`/`mul` plus
`global.get`. So this is i64-only.

## Fix shapes

1. Record i64 constants and i64 `add`/`sub`/`mul` in `initExpr` and teach
   `emitInitExpr` to fold them into the lo/hi pair. Correct, and matches what
   the i32 path already does.
2. Refuse the module with a diagnostic when an i64 global's initializer is an
   extended constant expression that `initExpr` cannot represent. Smaller,
   and strictly better than the current silent wrong answer.

Either is acceptable; do not leave it silent.
