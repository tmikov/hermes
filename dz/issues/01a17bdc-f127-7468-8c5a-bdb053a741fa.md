Word segmentation in `Intl.Segmenter` takes time quadratic in the number of
words of an unbroken run of Chinese, Japanese or Thai text, so a crafted
long run hangs the caller for tens of seconds.

Cause: ICU4X 2.3's word segmenter. For a run of a complex script,
`handle_complex` (`icu_segmenter-2.3.0/src/word.rs:961` for UTF-8, `:1015`
for UTF-16) segments the whole run with the dictionary once and stores the
breaks in `result_cache`. After that, every `RuleBreakIterator::next`
(`icu_segmenter-2.3.0/src/rule_segmenter_v1.rs:59`) rebuilds the vector of
the breaks still pending (`skip(1).map(|r| r - i).collect()`), so a run
with k breaks costs O(k^2). ICU4X 2.4 replaced the rebuild with a
`ResultCache` that keeps the pending breaks by distance
(`icu_segmenter-2.4.0/src/rule_segmenter_v1.rs:21`, `:131`, `:158`).

Measured in the Debug ASan build (cmake-build-asan, aaa8490c7), through
`containing`:
- `"我爱北京天安门".repeat(30000)` (210,000 code units): 21.9 s;
- `"ก"` followed by 199,999 tone marks U+0E48 (200,000 code units),
  `containing` at the last index: 60 s.

Repro:

    new Intl.Segmenter("zh", {granularity: "word"})
      .segment("我爱北京天安门".repeat(30000)).containing(0)

Why it is not fixed now: Cargo keeps one 2.x version of a crate, so
`icu_segmenter` 2.4 cannot sit next to the rest of ICU4X at 2.3. `icu` 2.3
requires `icu_segmenter ~2.3.0`, and the 2.3 and 2.4 crates require
`icu_collections` and `icu_locale_fallback` at their own minor version.
The user chose to wait for the full ICU4X 2.4 upgrade (CLDR 49) rather than
vendor or patch ICU4X. The spec records the limitation under "Data" ->
Segmenter and "Risks".

Fix: the ICU4X 2.4 upgrade. Add regression tests then, in Rust and in lit
(through `containing` at the last index): a 200,000-code-unit Han run and a
200,000-code-unit Thai base-plus-marks run, each segmented in well under a
second, asserting on the boundaries.
