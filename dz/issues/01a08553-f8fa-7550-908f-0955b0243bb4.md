Any JS value is a valid externref, undefined included, and the Wasm link path's raw-value arm
accepts it. But a raw undefined can never reach that arm, because the import-object lookup
upstream cannot distinguish a property that is present and holds undefined from one that is
absent: both produce LinkError: module has no import e.<name>.

So this succeeds nowhere:

    new WebAssembly.Instance(mod, {e: {b: undefined}})   // for (import "e" "b" (global externref))

and it fails with a message saying the import is missing, which is not what happened.

Pre-existing, and outside the link path itself -- the link path is correct here; the lookup that
feeds it is what loses the distinction. Found while implementing reference-typed global imports,
where it is newly observable because undefined became a legal value to import rather than a type
error.

The limitation is asserted in test/wasm/e2e-global-ref-import.wat so it is on record and a future
fix will have a test that changes rather than a silent behaviour swap.

Whoever fixes it should check the same lookup for the other import kinds -- nothing here suggests
globals are special, it is just where it was noticed.

    Superseded in part, after measuring against node v24.13.1.

    The EXTERNREF half is fixed in Task 5 of the reference-types plan. An immutable externref global import is now exempt from the missing-import guard, so both a present-and-undefined property and an absent one link and hand the module undefined -- which is what node does: it has no missing-import concept for globals at all, reading the property, taking undefined when absent, and applying the type rule.

    The test no longer pins the LinkError for externref. It asserts the link succeeds, for both the present-undefined and the absent shapes.

    What remains is the MESSAGE for every other case: a funcref or numeric global, and every non-global import kind, still say the import is missing where node names a type error. That half is filed separately, with the measurements, as 01a0855d-6b5b. This issue can be closed in favour of it once someone confirms nothing else here is outstanding.
