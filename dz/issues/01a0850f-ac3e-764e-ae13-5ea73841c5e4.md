WasmIRGen.cpp:340-357 narrows i32 and i64 call results with createAsInt32Inst, but pushes f32 and
f64 results onto the Wasm stack UNCOERCED.

The results are read out of the numeric return buffer with an ordinary createLoadPropertyInst
(WasmIRGen.cpp:351-355), and that buffer is built from a REPLACEABLE Float64Array
(WasmIRGen.cpp:1481). So a replacement storage object whose getter returns a non-Number -- a
string, say -- has that value pushed onto the Wasm stack as though it were an f64, with no
coercion anywhere on the path.

One symptom was found during the reference-types work: WasmIRGen.cpp:7993 pops such a value and
hands it straight to emitGlobalSet, so a string reaches the internal global setter for a NUMERIC
global through ordinary compiled Wasm. That specific refusal is now tested (a gtest on the
direct-builtin harness), and the report for that work claimed the path was reachable only through
untrusted bytecode -- which was wrong, and is corrected.

But the global setter is only one consumer. The same uncoerced value reaches EVERYTHING
downstream of a multi-value call that produces an f32 or f64 result. The i32/i64 rows are narrowed
and the float rows are not, which looks like an oversight rather than a decision.

Not fixed during the reference-types work: it is not a reference-type defect, the fix belongs with
the numeric return buffer, and that buffer already carries two filed defects -- 01a0820d-5190
(nested-call buffer mismatch) and 01a0821a-1093 (interceptable storage). This is a third, and
whoever takes any of them should look at all three together: they share a cause, which is that the
numeric result path uses ordinary property operations on script-replaceable objects.

What is NOT known: whether an uncoerced non-Number reaching an arithmetic instruction is caught
downstream by some later narrowing, or silently produces a wrong value. Nobody has traced past the
global-setter symptom.

    CORRECTION AND REFINEMENT to the text above, from a second review. Two of my original claims were
    too weak and one was wrong.

    1. "Nobody has traced past the global-setter symptom" -- source inspection now distinguishes two
       downstream routes, and they behave differently:

       IMMEDIATE ARITHMETIC IS SAFE. An f64.add on the uncoerced value applies asNumber, and
       WasmIRGen.cpp:5776 emits a real conversion for an untyped operand.

       THROUGH AN INTERNAL CALL IT IS NOT. WasmIRGen.cpp:4229 forwards call arguments unchanged; the
       callee stores parameters into numerically TYPED slots without conversion (WasmIRGen.cpp:2970);
       asNumber can then skip the conversion because the slot is already typed as a number; FAdd
       lowers to AddN, whose interpreter implementation calls getNumber() -- unchecked in release
       (Interpreter.cpp:2501).

       So a non-Number can reach an unchecked getNumber() in a release build by being passed through
       an internal call. That is a violated type assumption, not merely an odd value. It deserves a
       reproduction through a typed internal callee.

    2. f32 is worse than "uncoerced". Obtaining a Number is not sufficient for an f32 result -- the
       value also has to be rounded to f32 precision, and nothing on this path does that. The
       asymmetry with i32/i64 is therefore about precision as well as type.

    3. WRONG CLAIM, retracted: I wrote that this shares a cause with 01a0820d-5190 (nested-call buffer
       mismatch) and 01a0821a-1093 (interceptable storage), namely ordinary property operations on
       script-replaceable objects. That holds for 01a0821a-1093. It does NOT hold for 01a0820d-5190:
       buffer-identity mismatch remains possible even with private, non-interceptable storage, because
       the defect there is passing one buffer and reading a different one. Do not treat the three as
       one fix.

    THE FIX SPLITS IN TWO, and only one half is addressed by the buffer work.

    01a0821a-1093 now carries a worked-out proposal for making the numeric return buffer
    non-interceptable (three options, with the middle one shown to be dominated). If any of them
    lands, THE UNSOUNDNESS RECORDED HERE GOES AWAY: a pristine Float64Array can only yield numbers, so
    wasmValTypeToIRType(F64) = Type::createNumber() stops being a lie, and asNumber's
    isNumberType() short-circuit stops being reachable with a non-number.

    THE OTHER HALF SURVIVES ALL OF THEM: f32 results are not rounded to f32 precision. The f32 and f64
    arms of the result load are the same arm --

        case WasmValType::F32:
        case WasmValType::F64: {
          uint32_t idx = byteOff / 8;
          auto *val = builder_.createLoadPropertyInst(getRbF(), ...);
          push(val);

    -- and the buffer is a Float64Array, so an f32 result comes back with f64 precision. Whoever fixes
    this should fix both halves or say explicitly which one they are doing: making the buffer pristine
    without rounding f32 leaves a correctness bug with a much more ordinary trigger, because it needs
    no replaced global at all.

    FRAMING WORTH KEEPING: the `number` annotation is a PROMISE. The i32/i64 arm keeps it, with
    createAsInt32Inst. The f32/f64 arm does not. Every other producer of an f64 in this compiler keeps
    it. So the annotation is not wrong -- one path violates it, and the fix belongs on that path
    rather than on the annotation.
