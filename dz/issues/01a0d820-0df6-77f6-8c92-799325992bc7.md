Found 2026-09-25 while writing Task 6 of the Wasm native-backend plan
(test/wasm/native-trap.wat, test/wasm/native-try.wat), then reduced and
measured directly against the two compiler drivers.

## Symptom

`shermes -c` refuses to compile a `.wasm` module that `hermesc --wasm
-emit-binary` compiles fine, whenever a function's Wasm source contains an
explicit `unreachable` that is not the function's very last instruction (so
WasmIRGen emits code after it). Minimal reproducer:

```wat
(module
  (func (export "boom") (unreachable)))
```

```
$ hermesc --wasm -emit-binary -out out.hbc boom.wasm; echo $?
0

$ shermes -exported-unit=m -c -o out.o boom.wasm
...
%BB1 unreachable from entry in the Dominance Tree in function "wasm_func_0"
IRGen produced invalid IR
$ echo $?
1
```

`hermesc --wasm -O0 -emit-binary` reproduces the same failure ("Lowered IR
verification failed"), so this is not really an O0-vs-OMax question -- it is
an ordering question, and shermes always runs it in the failing order
regardless of -O level (see below).

## Cause

WasmIRGen always emits a trailing basic block after `unreachable` (a
`ReturnInst` in a block the `UnreachableInst` above it makes statically
unreachable from entry). That block is provably dead and DCE removes it --
but only if DCE runs before the block is checked.

`lib/CompilerDriver/CompilerDriver.cpp`'s `processWasmFile` (used by
`hermesc --wasm`) goes straight from `compileWasmModule` into the optimizer
switch, with no pre-optimization verify at all; genOptions.verifyIR only
checks LOWERED (post-optimization, post-bytecode-gen) IR. At any level above
O0 the dead block is gone by then.

`tools/shermes/shermes.cpp`'s wasm-input branch does something different: it
falls through to the SAME "Verify the IR before we run optimizations on it"
block that the JS-source path uses (around shermes.cpp:1053), which calls
`verifyModule` unconditionally BEFORE the `cli::OptimizationLevel` switch --
so this runs before DCE regardless of what `-O` level is requested. shermes's
default level is OMax, but it never gets there for this module: it is
rejected before the optimizer sees it.

## Why it matters beyond the two tests that found it

`unreachable` is not an obscure opcode. It is how Rust panics and C/C++
`abort()`/assertion failures compile to Wasm (rustc and clang/LLVM's wasm32
targets both lower unreachable-code and panic paths to `unreachable`), so a
large fraction of real, non-hand-written `.wasm` modules use it -- often in
an untaken branch (an unreachable `default:` arm, an assertion), which is
exactly the shape that trips this: the source has code after it, even though
nothing dynamically reaches that code. Those modules fail to compile through
`shermes -c` while compiling fine through the bytecode path -- a native/
bytecode backend divergence in module acceptance, not just in some computed
value.

## Reproduced with

test/wasm/native-trap.wat (a bare `unreachable` function body) and
test/wasm/native-try.wat (adapted from e2e-try-delegate.wat, whose module has
two `catch_all unreachable` handlers) both hit this; the other six tests in
that batch (native-e2e-add, native-data-segment[-neg], native-multivalue,
native-call-indirect, native-bulk-memory) do not, because none of their
source functions contain an explicit `unreachable`. Both failing tests are
marked `XFAIL: *` referencing this issue rather than weakened, matching the
existing convention (e.g. test/wasm/spec/elem.wast) for a known, tracked
defect. Un-XFAIL them once this is fixed -- they will then be the regression
tests for it.

## Suggested shape of the fix

Make shermes's wasm-input branch match `processWasmFile`'s order: skip (or
move after optimization) the early `verifyModule` call for wasm-compiled
modules, or run DCE before it. The branch already special-cases wasmInput
earlier (compileWasmModule instead of parseJS/generateIRFromESTree); the
early verify a few lines later does not have a matching wasmInput
exemption and should.
