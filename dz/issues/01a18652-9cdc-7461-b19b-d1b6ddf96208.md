The plugin library carries ICU4X's full compiled data for every locale
plus the plugin's generated CLDR files, and is about 20 MB on every
platform (measured in Phase 6, spec "Packaging" -> Sizes):

- Linux x86_64: 19,931,056 bytes stripped;
- Android: 18,455,688 (armeabi-v7a) to 19,925,832 (x86_64) per ABI, so
  about 77 MB across the four ABIs of the AAR;
- Apple: about 19.7-19.9 MB per architecture (39.8 MB for the two-
  architecture macOS, Catalyst and iOS simulator slices);
- Windows: 19,026,944 (x64), 18,877,440 (arm64).

For comparison, the stripped arm64 libhermesvm.so is about 2.9 MB, so an
app that ships the plugin grows by several times the size of the VM.

Size was a non-goal through Phase 7 ("Binary size, for now" in the spec's
Non-goals): nothing has been done to reduce it. The spec's "Size work
comes later" item says where it would start: smaller presets from a
checked-in script that runs icu4x-datagen once and commits its output,
picked up through ICU4X_DATA_DIR, driven by measurements of what each
constructor's data costs (the spec's per-phase size table shows the
growth: Phase 2 2.0 MB stripped, Phase 3 5.1 MB, Phase 4 10.2 MB,
Phase 5 19.9 MB).

Possible directions, to be measured first: a locale subset preset for
embedders that want it, dropping data the JS layer never reaches,
compressing rarely used tables, and the split between ICU4X data and the
plugin's own generated files.
