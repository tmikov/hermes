Split out from `01a074ce-ac97` on 2026-09-07, when reference-typed globals
were scoped for implementation and v128 was deliberately left out.

The JS API says a module MAY export a v128 global: the exports object gets a
real `WebAssembly.Global`, `.value` on it throws a TypeError, and
`new WebAssembly.Global({value: "v128"})` throws. Measured in node v24.13.1:

```
exported v128 global:                  Global object; .value -> TypeError
new WebAssembly.Global({value:"v128"}) -> TypeError
```

So JS can never read or write one; the object exists only so the export is
not missing.

## What Hermes does instead

After the reference-typed-globals work, a v128 global export is DIAGNOSED --
refused with a message saying SIMD is unsupported -- rather than exported as
a shell. That was chosen deliberately over building the object, because:

- SIMD is unsupported engine-wide. Every v128 opcode path warns and
  degrades; there is no 128-bit value in the engine to put behind the object.
- `BinaryReaderHermesIRGen` has no `v128.const` init handler, so a v128
  global's initializer falls through to the default `InitKind::I32Const` and
  the slot silently holds the number `0` (see `01a079fe-eff6` for the
  same class of fallback bug on i64).
- A `Global` claiming to be v128, whose `.value` throws by design, backed by
  a slot holding a fictional `0`, makes a conformance test pass without the
  value being real.

## Why this issue exists anyway

We do want the fixtures to pass eventually. Node's
`test/fixtures/es-modules/dep.wasm` and `globals.wasm` each carry a v128
global alongside their reference-typed ones, so they stay unrunnable under
Hermes until this is done -- those two are the only 2 of 42 Node `.wasm`
fixtures that fail.

## Done looks like

- `WasmValType::V128` maps to a real `JSWebAssemblyGlobal::ValType`.
- An exported v128 global produces a `Global` object.
- `Global.prototype.value` throws a TypeError for it, get AND set.
- `new WebAssembly.Global({value: "v128"}, ...)` throws a TypeError.
- The compile-time diagnostic added by the reference-types work is removed.
- Node's `dep.wasm` and `globals.wasm` instantiate.

Ideally this lands with, or after, real SIMD support, so the storage behind
the object is a genuine 128-bit value rather than a placeholder. If it lands
first, say so in the code: a reader must not conclude from the object's
existence that the engine has a v128 value.

    THE DIAGNOSTIC EXISTS NOW, and this is its exact text, so the shell work knows what to delete.

    Added by task 12 of the reference-types plan (branch wasm-new). Message, verbatim:

        exported global "<name>" has type v128, and SIMD is not supported

    Where it comes from: WasmIRGen::validateGlobalExportTypes() in lib/WasmIRGen/WasmIRGen.cpp,
    called from finalizeModule() immediately after validateExportIndices() and before any of the
    export loops run, so no IR is emitted for the refused module. It sets errorMsg_ and returns
    false, which is the same channel validateExportIndices() uses; WasmCompile.cpp turns that into
    the compile failure.

    How it surfaces, both routes:

        $ hermesc --wasm -emit-binary -out x.hbc x.wasm
        Error: exported global "g" has type v128, and SIMD is not supported     rc=2

        new WebAssembly.Module(bytes)
        -> CompileError: exported global "g" has type v128, and SIMD is not supported

    A CompileError from `new WebAssembly.Module`, not a TypeError from
    `new WebAssembly.Instance`, which is what the export path used to produce by way of
    wasmMakeGlobal's range check.

    It covers all three shapes a v128 global export can take -- a defined immutable one, a defined
    mutable one, and a re-exported imported one -- because the check derives the type for every
    exported global index before the export loop, rather than sitting inside the loop body. (The
    loop publishes an imported mutable global by storing the object it arrived as and skipping the
    rest of the iteration, so a check placed there would miss that third shape.)

    ## What to remove when the shell is built

      - WasmIRGen::validateGlobalExportTypes() and its declaration in WasmIRGen.h, plus the call
        and the explanatory comment in finalizeModule(). globalTypeAt(), added alongside it, is
        also used by the export loop and should stay.
      - test/wasm/compile-invalid-v128-global-export.wat and
        test/wasm/compile-invalid-v128-global-reexport.wat, which assert the message.
      - The paragraph in globalValTypeCode()'s doc comment (WasmIRGen.cpp) that says the export
        side no longer reaches it with a v128 type. Note what that comment also says and what the
        shell work does NOT get to delete: the IMPORT side is still unscreened, because an
        immutable global import may be satisfied by a raw JS value and the raw branch's fallback
        arm accepts a Number for v128.

    CORRECTION to the "How it surfaces" block above: both routes emit an extra line on stderr
    first, and the block dropped it. A future implementer diffing output before and after
    removing the diagnostic would have been surprised by it.

    The real output, captured whole (stdout and stderr merged):

        $ hermesc --wasm -emit-binary -out x.hbc x.wasm
        0000027: error: EndModule callback failed
        Error: exported global "g" has type v128, and SIMD is not supported
        rc=2

        $ hermes -Xenable-untrusted-bytecode-from-js t.js
        validate: true
        0000027: error: EndModule callback failed
        caught: CompileError: exported global "g" has type v128, and SIMD is not supported
        survived
        rc=0

    The first line is wabt's, not Hermes'. A refusal raised inside
    WasmIRGen::finalizeModule() is propagated by returning wabt::Result::Error from
    BinaryReaderHermesIRGen::EndModule(), and wabt's binary reader prints its own line before
    Hermes reports the message. It is not specific to the v128 diagnostic -- every
    finalizeModule() refusal surfaces this way -- but it is the first one a test in the tree
    actually exercises, because the other two compile-invalid-*.wat modules are refused earlier
    by validateWasmBinary and never enter ReadBinary.

    The message byte offset (0000027 here) is the module's, so it varies per module; the two
    lit tests do not check that line.
