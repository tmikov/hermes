Pre-existing on `wasm-new` at a460f1457; reproduces with the task-9
reference-types change reverted, so it is independent of it.

A `try` that declares a result type and whose body reaches the end of the
block without throwing or branching produces IR the lowered-IR verifier
rejects:

```wat
(module
  (import "e" "boom" (func $boom))
  (tag $t_i32 (export "t_i32") (param i32))
  (func (export "c") (result i32)
    (try (result i32)
      (do (call $boom) (i32.const 9))
      (catch $t_i32))))
```

```
Operand %8 must dominate the Instruction %2 in function "wasm_func_1"
error: Lowered IR verification failed
Emitted 1 errors in the backend. exiting.   (exit 8)
```

The continuation block ends up using the catch handler's payload load
directly instead of a phi, while `TryEndInst` also branches to it from the
try body. `WasmIRGen::onTry` does call `createResultPhis(contBlock, ...)`,
and `onCatch`'s fall-through path emits `TryEndInst(catchBlock, contBlock)`
without a matching `addBranchPhiOperands`, so the try-body edge contributes
no phi operand. That is where to start, not a diagnosis.

No existing test has a `try` with both a result type and a body that falls
through: `e2e-try-catch.wat`'s result case ends its body in `throw`.

Issue 01a0460b-abb6 (H21) mentions this in passing as a "separate
pre-existing IRGen bug"; recording it on its own so it can be worked and
closed independently. `test/wasm/e2e-exception-payload-ref.wat` routes its
results through locals to stay clear of it, and says so.

    Fixed 2026-09-14. The diagnosis in the description was right.

    onCatch's first-clause path emitted TryEndInst(catchBlock, contBlock) for the
    try body's fall-through WITHOUT calling addBranchPhiOperands, so the body's
    results never reached the continuation's phis. The phi then had one operand
    for two predecessors, and the operand it did have was the catch handler's
    payload load, which does not dominate the continuation -- hence

        Operand %8 must dominate the Instruction %2 in function "wasm_func_1"

    The body's own result was not merely unused: it never reached the IR at all.

    TWO PATHS HAD IT, not one. onCatchAll's first-handler path is the same code
    with the same omission, so `(try (result i32) (do ... ) (catch_all ...))` was
    equally broken. onDelegate already did it correctly, which is what the fix
    copies.

    TWO HALVES, both necessary and both demonstrated:

      - addBranchPhiOperands(entry), which contributes the body's results to the
        continuation phis. Without it: the verifier failure above.
      - entry.branchTargeted = true. onEnd computes
        `unreachable_ = !fallsThrough && !entry.branchTargeted` for the
        continuation, where fallsThrough is about the last HANDLER. If every
        handler rethrows, the continuation is reachable only from the body's
        edge, and without this it is treated as unreachable. Measured: with this
        half alone removed and the phi half kept, the new test still fails.

    Pinned by test/wasm/e2e-try-result-fallthrough.wat, which covers a single
    result, two results (so operand ORDER matters and not only the count), a
    nested try, catch_all as the first handler, and the all-handlers-rethrow shape
    -- each in both the fall-through and the caught direction.

    check-hermes 4585/16/197/0 unexpected. The spec suite's exception tests and
    the existing try/catch e2e tests are unchanged.
- 2026-09-14T05:47:11.924Z  Tzvetan Mikov <tmikov@gmail.com>  comment
    An external review of the fix found a second defect it ran into rather
    than caused, so the commit carries both.

    `onTry` recorded the stack height at the `try` WITHOUT subtracting the
    block's parameter slots, which `onBlock` and `onLoop` have always done.
    Nothing had ever compiled a `try` with parameters, so it went unnoticed.
    The params were counted as still sitting on the enclosing stack while
    the body consumed them as its own, and the recorded height is also what
    a catch handler is restored to -- wrong for the same reason, since an
    exception unwinds past whatever the body had already consumed.

        (func (result i32)
          (i32.const 40) (i32.const 2)
          (try (param i32) (result i32) (do) (catch_all (i32.const 99)))
          (i32.add))

    Before the fall-through fix this returned 101 -- the handler's 99 plus
    the parameter nobody had removed -- instead of 42. Once the body's edge
    started popping its result, the same mismatch left the stack one below
    the recorded height, `onEnd` refilled it with a null, and the compiler
    dereferenced that in `Type::isNumberType`. A sibling shape whose body
    throws crashed the same way BEFORE the fall-through fix.

    `onTry` now takes the parameter types, like `onBlock`, and subtracts
    their slots. `p`, `pi64` and `pmix` in the test cover a plain parameter,
    an i64 parameter (two slots, so a fix counting parameters rather than
    slots is off by one) and mixed parameters over a sentinel, each in both
    directions.

    Four further defects the review turned up are filed separately, none of
    them touched here: 01a09e72-a261 (br_table to a try label drops its
    result operands), 01a09e72-e936 (br out of a try body never closes the
    region), 01a09e72-e95d (delegate ignores its depth) and 01a09e72-754b
    (an i64 result in unreachable code crashes the compiler).
