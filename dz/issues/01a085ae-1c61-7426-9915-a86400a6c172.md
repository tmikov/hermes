peekThroughAsInt32 (lib/WasmIRGen/WasmIRGen.cpp:115-121) unwraps an AsInt32Inst only when its
operand isBooleanType(). It has two callers: onIf (:3804) and onBrIf (:4112).

The guard appears never to be true. The comparisons that feed these branches are built with
IRBuilder::createBinaryOperatorInst (lib/IR/IRBuilder.cpp:901-905), which leaves a comparison
typed `any` at IR-generation time -- type inference does not run until later, and
include/hermes/IR/Instrs.h:3302 assigns no boolean type either. So when onBrIf asks
peekThroughAsInt32 to look through, the operand is `any`, the guard is false, and the AsInt32Inst
survives.

Observed on a module exercising `ref.is_null` feeding `br_if`, at both optimization levels:

  -O0     wasm_func_20:  %7 = AsInt32Inst (:number) %6: any
                         CondBranchInst %7: number, %BB2, %BB3
  default wasm_func_20:  %2 = AsInt32Inst (:number) %1: boolean
                         CondBranchInst %2: number, %BB1, %BB2

Note the default-level dump shows the operand IS boolean by then -- but that is after type
inference, long after onBrIf ran and made its decision.

The helper predates the reference-types work (introduced in b62b60d44) and neither caller was
observed to unwrap anything. Nothing is broken by this: branching on the AsInt32Inst is correct,
just one instruction longer than intended.

What to check before acting: whether the guard is ever true for any opcode that feeds onIf or
onBrIf -- a comparison built elsewhere and already typed boolean at IRGen time would satisfy it.
If none exists, the helper is dead and either the guard should move after type inference or the
helper should go.

Found while reviewing a comment that claimed the helper DOES discard the AsInt32Inst on the br_if
path. The comment was corrected; this issue records the underlying question the comment raised.

    CORRECTION -- the framing above is WRONG and would misdirect anyone who picks this up. The
    question it poses ("whether the guard is ever true for any opcode") was already answered by a
    passing test in this repository when the issue was filed. I did not check before filing.

    THE GUARD IS OFTEN TRUE. peekThroughAsInt32 unwraps normally for ordinary comparisons:

      onI32Eq / onI32LtS (WasmIRGen.cpp:3536-3568) build with createFCompareInst, and FCompareInst's
      constructor (include/hermes/IR/Instrs.h:6051) calls setType(Type::createBoolean()) explicitly.
      The guard therefore sees a boolean operand and unwraps.

      test/wasm/cond-branch-peephole.wat pins exactly this and passes today. Its CHKO0 checks show
      `%[[CMP0]] = FLessThanInst (:boolean)`, `AsInt32Inst (:number) %[[CMP0]]: boolean`, and
      `CondBranchInst %[[CMP0]]: boolean` -- the branch consuming the comparison directly, with the
      AsInt32Inst bypassed. That is the helper doing its job.

    THE ACTUAL SCOPE, which is much narrower: the guard is false only for comparisons built with
    createBinaryOperatorInst, because BinaryOperatorInst's constructor (Instrs.h:3300-3306) sets NO
    type, so the comparison is `any` at IR-generation time. onRefIsNull is such a caller. So a
    ref.is_null feeding br_if or if branches on the AsInt32Inst rather than on the comparison, where
    an i32.eq feeding the same br_if does not.

    So this is not a dead helper. It is an INCONSISTENCY: two comparison-building routes produce
    different branch lowering for the same source-level shape, and the difference is invisible at the
    call site -- it depends on which constructor the opcode handler happened to use.

    Worth deciding rather than leaving: either give the strict-equality comparison a boolean type at
    construction the way FCompareInst does, or move the peek to after type inference so it does not
    depend on what the constructor happened to set. The first is smaller; the second removes the class
    of problem.

    Nothing is broken either way: branching on the AsInt32Inst is correct, just one instruction longer.
