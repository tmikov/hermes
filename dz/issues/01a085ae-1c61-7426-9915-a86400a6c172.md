peekThroughAsInt32 (lib/WasmIRGen/WasmIRGen.cpp:115-121) unwraps an AsInt32Inst only when its
operand isBooleanType(). It has two callers: onIf (:3804) and onBrIf (:4112).

The guard appears never to be true. The comparisons that feed these branches are built with
IRBuilder::createBinaryOperatorInst (lib/IR/IRBuilder.cpp:901-905), which leaves a comparison
typed `any` at IR-generation time -- type inference does not run until later, and
include/hermes/IR/Instrs.h:3302 assigns no boolean type either. So when onBrIf asks
peekThroughAsInt32 to look through, the operand is `any`, the guard is false, and the AsInt32Inst
survives.

Observed on a module exercising `ref.is_null` feeding `br_if`, at both optimization levels:

  -O0     wasm_func_20:  %7 = AsInt32Inst (:number) %6: any
                         CondBranchInst %7: number, %BB2, %BB3
  default wasm_func_20:  %2 = AsInt32Inst (:number) %1: boolean
                         CondBranchInst %2: number, %BB1, %BB2

Note the default-level dump shows the operand IS boolean by then -- but that is after type
inference, long after onBrIf ran and made its decision.

The helper predates the reference-types work (introduced in b62b60d44) and neither caller was
observed to unwrap anything. Nothing is broken by this: branching on the AsInt32Inst is correct,
just one instruction longer than intended.

What to check before acting: whether the guard is ever true for any opcode that feeds onIf or
onBrIf -- a comparison built elsewhere and already typed boolean at IRGen time would satisfy it.
If none exists, the helper is dead and either the guard should move after type inference or the
helper should go.

Found while reviewing a comment that claimed the helper DOES discard the AsInt32Inst on the br_if
path. The comment was corrected; this issue records the underlying question the comment raised.
