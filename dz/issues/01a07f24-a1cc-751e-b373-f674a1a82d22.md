Found 2026-09-08 by external review of the H20 fix design, then measured.
Pre-existing and independent of H20 -- isolated below with a CONSTANT offset,
so the H20 ordering bug plays no part.

An active element segment whose range runs past the end of its table must
trap at instantiation. Hermes instantiates silently instead.

## Reproducer

```wat
(module
  (table 6 funcref)
  (func $f0 (result i32) (i32.const 100))
  (func $f1 (result i32) (i32.const 200))
  (elem (i32.const 5) $f0 $f1)   ;; slots 5 and 6 on a 6-slot table
  (type $t (func (result i32)))
  (func (export "call") (param i32) (result i32)
    (call_indirect (type $t) (local.get 0))))
```

```
Node v24.13.1: trapped: RuntimeError: WebAssembly.Instance(): table index is
               out of bounds
Hermes:        instantiated (no trap)
```

An empty active segment placed entirely out of range is the same case with no
writes at all, and is likewise not checked.

## Mechanism

`createTables`'s active-element loop computes `offset + i` per entry and
writes immediately, with no check of the segment's whole range against the
table size (`WasmIRGen.cpp`, the "Apply active element segments" loop).

Nothing supplies the check transitively. The write funnel
(`wasmTableSetSlot` -> `setWasmTableSlot`) stores through
`JSObject::setOwnIndexed`, and indexed array storage EXPANDS rather than
refusing -- so an out-of-range element grows the backing array instead of
trapping. That is a JS array operation, not a Wasm table-range check.

The contrast is instructive: `table.init` DOES check its destination range
before copying (`HermesBuiltin.cpp`, the bulk-table path). The instantiation
path just never grew the equivalent.

## Consequence

A valid module that the spec requires to be REJECTED at instantiation is
accepted, and its table silently grows past its declared limits. Any later
reasoning that a table's backing array length equals its declared size is
then wrong -- worth checking whether anything depends on that.

## Fix

Bounds-check each active segment's full range (`offset + count <= tableLen`)
before writing any entry, and raise the trap the spec requires. The check has
to happen at instantiation and cover the empty-segment case, where there are
no writes to hang it off.

## Related

- `01a0460b-ab9a` (H20) -- the same loop, different defect. H20's fix
  (initializing globals before tables) makes a `global.get` offset produce
  the right number, which is a precondition for this check being meaningful
  for non-constant offsets, but the two are otherwise independent.
