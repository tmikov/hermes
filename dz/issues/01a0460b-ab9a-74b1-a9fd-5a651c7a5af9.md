Recorded as **H20** in the Wasm branch review (`wasm-old-rebased`). Pre-existing;
found 2026-08-26 reviewing the §4.4 internal-slots pass. Confirmed, not just
read: the §4.4 work rewrote this loop's body without noticing either bug.

## Bug 1 — the ordering

`createTables()` emits `LoadFrameInst globalVars_[slotIdx]` for an active element
segment whose offset is a `global.get` (`WasmIRGen.cpp:7054-7056`).
`createFunctions` calls `createTables()` at `:1513` and `initializeGlobals()` at
`:1517`, so the slot still holds `undefined` when the segment is placed. The
comment three lines above the read (`:7036-7038`) even says a `global.get` offset
"would require globals to be initialized first, which is not yet implemented" —
while the code goes ahead and emits it.

Module: `(import "e" "g" (global i32))` + `(elem (global.get $g) $f0 $f1)` on
`(table 6 funcref)`, `g = 2`. Correct answer is slots 2 and 3.

| path | result |
|---|---|
| `hermesc --wasm` (default `-O`) | **compile fails**: `PhiInst: NoType instruction has output in "__wasm_instantiate__"` -> `error: Lowered IR verification failed`, exit 8 |
| `hermesc --wasm -O0` | compiles; **both** functions land in slot 0 (`undefined + 1 = NaN`, `truncateToInt32 = 0`). Silent corruption |
| `new WebAssembly.Module(bytes)` | compiles; segment placed at 0 and 1 instead of 2 and 3. Silent wrong answer |

So the default path is a **hard compiler abort on a valid module**. Data segments
are unaffected — they are emitted after `initializeGlobals`.

## Bug 2 — the hard-coded first index (separate, same loop)

`WasmIRGen.cpp:7079-7080`:

```cpp
if (i == 0 && seg.offsetValue == 0) {
  idx = builder_.getLiteralNumber(0);
```

`seg.offsetValue` is left at its default `0` for a `GlobalGet` offset, so element
0 is hard-coded to table index 0 whatever the offset actually is. Even with the
ordering fixed this misplaces the first element of every `global.get`-offset
segment. It should be gated on `seg.offsetKind == I32Const`.

Both are present identically at the branch base.

    Fixed by "4c541388e" -- both bugs, in one commit.

    **Bug 1, ordering.** `initializeGlobals()` now runs BEFORE `createTables()`,
    so an active element segment's `global.get` offset loads a slot that has
    been written. Verified safe in both directions: `initializeGlobals` reads
    module metadata, `globalSlotIndex_`, `importedMutableGlobals_`,
    `importGlobalVals_`, previously initialized `globalVars_`, `retBufIVar_`
    (whose runtime store is earlier, not merely its creation) and
    `exportedFuncVars_` -- and never any table variable. The comment above
    `createExportedFunctions` now justifies itself by both callers, since a
    `ref.func` global initializer reads `exportedFuncVars_` too.

    **Bug 2, the first-element shortcut.** The predicate is now

    ```cpp
    bool firstIdxIsZero = seg.offsetExpr.size() <= 1 &&
        seg.offsetKind == WasmGlobal::InitKind::I32Const &&
        seg.offsetValue == 0;
    ```

    The `offsetExpr.size()` conjunct is load-bearing and the code says so: each
    `i32.const` overwrites the scalar fields while arithmetic only appends to
    `offsetExpr`, so an offset like `(i32.add (i32.const 2) (i32.const 0))`
    records `I32Const/0` and would otherwise take the shortcut.

    The stale comment claiming `global.get` offsets are "not yet implemented" is
    gone; the code below it emitted them all along, which is what made this a bug
    rather than a limitation.

    ## Verification

    The issue's own repro, `(elem (global.get $g) $f0 $f1)` on a 6-slot table
    with `g = 2`:

    ```
    before: hermesc --wasm     rc=8, "PhiInst (:notype)", full IR dump
            hermesc --wasm -O0 compiles; slot 0 -> 200, slots 1-5 uninitialized
    after:  hermesc --wasm     rc=0
            runtime            slot 2 -> 100, slot 3 -> 200, others uninitialized
    ```

    Three e2e tests, each failing pre-fix in a DIFFERENT way, which is why all
    three are kept: `e2e-elem-global-offset-order` (rc=8 compile abort),
    `e2e-elem-extconst-offset` (compiled, wrong slot -- the case an incomplete
    predicate ships broken), and `e2e-elem-extconst-global-offset` (both bugs at
    once).

    Full `check-hermes`: 4540 passes / 16 expected failures / 197 unsupported /
    0 unexpected, verified independently by the controller. One golden
    regenerated -- `compile-mixed-imports.wat`, whose global-store block moved
    ahead of the table stores; `irgen-table-init.wat` is plain %FileCheck, pins
    the full instantiate body and was untouched.

    ## Deliberately NOT fixed here

    Active element segments are still not bounds-checked against the table size,
    so an out-of-range segment grows the table instead of trapping. That is
    `01a07f24-a1cc`, found while designing this fix and kept separate so these
    tests can tell the two apart.
