Found 2026-09-08 by external review of the H20 fix design, then measured.
Pre-existing; no invalid module and no trusted `.hbc` required. Reachable
from ordinary script.

`createExportedFunctions` stamps each export wrapper with its signature via
an ordinary property store (`WasmIRGen.cpp`, the
`StorePropertyStrictInst ... "__wasm_type__"` on the wrapper closure). An
ordinary store WALKS THE PROTOTYPE CHAIN, so an inherited
`Function.prototype.__wasm_type__` accessor intercepts it.

This is the same class as H2 and as the `__wasm_type__` forgeries already
retired for globals, tables and memories. Functions and tags were left
behind: the comment at `WasmIRGen.cpp:864-866` says so outright -- "function
and tag imports still compare a `__wasm_type__` string".

## Two consequences, both measured

**1. User JS runs inside instantiation, with the wrapper as `this`.**

```js
Object.defineProperty(Function.prototype, "__wasm_type__", {
  configurable: true,
  set: function (v) { fired++; seen = typeof this; }
});
new WebAssembly.Instance(new WebAssembly.Module(bytes));
```

```
Hermes: setter fired during instantiation: 1 times; this was a function
Node:   setter fired during instantiation: 0 times
```

The setter also SWALLOWS the store -- the wrapper ends up with no own
`__wasm_type__` at all.

**2. The signature string can be FORGED.** The setter receives the module's
own export wrapper as `this` and can define whatever it likes on it:

```js
set: function (v) {
  Object.defineProperty(this, "__wasm_type__",
      {value: "func::FORGED", writable: true, configurable: true});
}
```

```
engine intended:            func::i
actually on the wrapper:    func::FORGED
```

## Why the forged value matters

It is not decorative. `WasmIRGen.cpp:935-951` LOADS `__wasm_type__` off an
import value and compares it, and that is how a cross-module FUNCTION import
is type-checked; the tag import path at ~1386 does the same.

So: module A exports a function, script forges its type string during A's
instantiation, module B imports that function under a different declared
signature, and B's import check compares against the forgery and accepts it.
That is type confusion at a cross-module call boundary -- a Wasm function
entered with a signature it was not compiled for.

## Fix

Stamp the signature somewhere script cannot name or intercept, the way the
Exported Function brand already works: `wasmSetFuncInfo` puts the internal
closure and the interned type id in INTERNAL properties, which script can
neither read nor write nor shadow. The function and tag import paths should
compare against that instead of a named string property.

That also removes the last `__wasm_type__` publication, finishing the job the
global/table/memory work started -- at which point the property and its
literal can go entirely.

Note the store is currently interceptable even when nothing reads it back, so
the "user JS inside instantiation" half is worth closing regardless of the
forging half.

    FUNCTION HALF FIXED, 2026-09-13. Tags still open; this issue stays open for
    them.

    Export wrappers no longer publish __wasm_type__ at all. The function import
    check reads the interned type id that wasmSetFuncInfo already stamps in an
    internal property, through a new wasmFuncTypeId builtin. Hermes now matches
    Node v24.13.1 byte for byte on every case below.

    A THIRD CONSEQUENCE, not in the description above and worse than the forgery:
    the setter SWALLOWED the store, so a wrapper created while it was installed
    carried no signature at all and an importer handed that wrapper fell through
    to its "accepts any callable" path. Wrappers made earlier keep their own
    property, so this switches checking off for everything instantiated while
    the setter is in place rather than retroactively. The forgery has to pick a
    target signature; this needs no target.
    Measured, before the fix, on a genuine (i32)->i32 export imported as
    (f64)->f64:

      export carries __wasm_type__: func:i:i
      setter fired during instantiation: 1 times
      swallowed signature, mismatched import: linked, call(21) = 42
      mismatched import: LinkError                     <- the control, correct
      forged signature, mismatched import: linked, call(21) = 42
      plain JS callable: linked, call(21) = 42         <- correct, must stay

    and after:

      export carries __wasm_type__: undefined
      setter fired during instantiation: 0 times
      swallowed signature, mismatched import: LinkError
      mismatched import: LinkError
      forged signature, mismatched import: LinkError
      plain JS callable: linked, call(21) = 42

    WHAT THE FORGERY WAS ACTUALLY WORTH, since the description calls it type
    confusion at a cross-module call boundary. It is that, but an attacker gains
    nothing they did not already have: a plain forwarding function satisfies any
    function import, so the same wrong-signature call can be arranged without
    touching anything. Measured identical in Hermes and in Node. The check is
    worth keeping and worth making unforgeable -- Node enforces it too -- but its
    value is catching a genuine export wired to the wrong import, not stopping an
    attacker.

    A COUPLING THE SPEC SUITE CAUGHT. imports.wast:256 asserts that a tag import
    satisfied by a FUNCTION export is unlinkable. That was only ever refused
    incidentally: the tag check read the wrapper's "func:i:" and saw it differ
    from the expected "tag:f:". Removing the function stamp made it read
    undefined and link. The tag check now refuses an Exported Function explicitly,
    on the brand.

    STILL OPEN HERE: tags. createTagObjects still builds a plain object literal
    and stores __wasm_type__ on it with an ordinary store, so both halves --
    Object.prototype interception, and rewriting the string afterwards -- are
    live for tags. The fix is to make module-defined tags JSWebAssemblyTag cells,
    which already exist and already carry their signature in a C++ field, rather
    than inventing a second tag-type mechanism beside them. That pulls in
    extending JSWebAssemblyTag::ValType to cover reference types (JSWebAssembly-
    Global::ValType has them as a template) and the toNumber coercion in
    `new WebAssembly.Exception`, which is wrong for a reference param and
    overlaps 01a0460b-abb6. See also 01a09ce6-b138 on the cell kinds generally.
