**HIGH SEVERITY — sandbox escape.** A hardened embedder does not get a hardened
Worker.

`startWorker` (`API/hermes/extensions/Worker.cpp`) creates the child runtime
with a **default** config:

```cpp
auto workerRuntime = api->makeHermesRuntime(::hermes::vm::RuntimeConfig());
```

Nothing propagates the parent's configuration. Any `RuntimeConfig` field whose
default is the permissive value is therefore restored in the child, and script
reaches it just by calling `new Worker(...)`.

## What is actually restored

`hardenedHermesRuntimeConfig()` (`API/hermes/hermes.cpp`) is the engine's own
statement of what hardening means. It sets exactly five things, and **every one
of them defaults the other way**:

| setting | hardened | child gets |
|---|---|---|
| `EnableEval` | false | **true** |
| `ES6Proxy` | false | **true** |
| `EnableHermesInternal` | false | **true** |
| `EnableHermesInternalTestMethods` | false | **true** |
| `RandomizeMemoryLayout` | true | **false** |

So an embedder that deliberately disabled `eval` and `HermesInternal` in its
runtime hands script a Worker with both switched back on, plus the internal
*test* methods, plus memory-layout randomization turned off.

## What is NOT affected, to keep the scope honest

`EnableUntrustedBytecodeFromJS` defaults to **false**, so the child is never
*more* permissive than the parent on the Wasm/Worker bytecode gate closed by
"Stop a Worker running Hermes bytecode that came from JavaScript". A hardened
parent yielding a default child is strictly more restrictive on that one flag.
This issue is about the flags whose defaults point the other way.

Exploitability is bounded: it requires an embedder who bothered to harden. An
embedder on defaults is already in the permissive position, so nothing changes
for them.

## Why the cheap fix does not work

The parent's config cannot be recovered at the point of use. `vm::Runtime`
retains `enableEval` and a Proxy flag as bitfields, but **not**
`enableHermesInternal`, **not** `randomizeMemoryLayout`, and not most of the 33
`RuntimeConfig` fields -- the config object itself is consumed by the
constructor and dropped. So the trick used for the bytecode gate (read the flag
off the live `vm::Runtime` at extension-install time) is not available here.

## Options considered

1. **Enumerate a security subset** into `ExtensionsConfig` as plain bools.
   Preserves the extension-header boundary (0 of 11 headers include a
   `hermes/` header) and fixes today's five. Rejected as the primary fix: the
   maintenance failure is silent and defaults permissive. Someone adds a
   hardening flag to `RuntimeConfig`, nobody updates the list, and workers
   quietly stop inheriting it -- a bad property for a security boundary.

2. **Retain the parent `RuntimeConfig`** on `HermesRuntimeImpl` and pass it
   down. No enumeration, but it puts a Hermes type in an extension header,
   which is the boundary that ruled this shape out once already.

3. **Hand the extension a child-runtime factory** (recommended).
   `ExtensionsConfig` carries a
   `std::function<std::unique_ptr<jsi::Runtime>()>` -- a std type, so the
   header stays Hermes-free. `makeHermesRuntime` already has the parent config
   in scope and captures it by value when building the lambda, so nothing needs
   retaining and no flag list exists to fall out of date. `Worker.cpp` stops
   choosing a config and just asks for a child runtime.

Option 3 also fixes the underlying design fault rather than its symptom: an
extension should not be deciding the configuration of a runtime it creates.
Enumerating flags would leave that decision in the wrong place.

## Decisions needed before implementing

Inheriting *everything* is not obviously correct:

- **GC config.** Every worker would get the parent's heap sizes; N workers at a
  large max heap is a different resource story than today's defaults. The child
  may want its own GC config.
- **Crash manager / debugger settings.** A crash manager shared across threads,
  or a child that believes it has a debugger attached, may not be intended.

Suggested shape: inherit by default via the factory, with an explicit and
commented override for the fields that should not cross the thread boundary --
so the safe direction is the default and each exception is a visible decision.

## Verifying a fix

A test should harden the parent (`withEnableHermesInternal(false)`, say),
create a Worker, and assert the child cannot see what the parent disabled.
Note the failure mode is silent, so the test must assert the child's *absence*
of the capability rather than that construction succeeded.
