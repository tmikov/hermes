The Wasm work added SEVEN cell kinds, taking CellKinds.def from 80 to 87.
That is a lot of permanent VM surface -- a class, a vtable, a BuildMeta, GC
metadata, and a case in every switch over cell kinds -- for one optional
feature. Most of them should go.

WHAT EACH ONE ACTUALLY CARRIES, all subclassing JSObject directly:

  Module      std::unique_ptr<WasmModuleData>            finalizer
  Instance    NOTHING                                    -
  Memory      GCPointer<JSArrayBuffer>, uint32_t         -
  Table       GCPointer<JSArray> x3, uint32_t            -
  Global      GCHermesValue, ValType, bool,
              GCPointer<Callable> getter_/setter_        -
  Tag         std::vector<ValType>                       finalizer
  Exception   GCPointer<JSWebAssemblyTag>,
              GCPointer<JSArray>                         -

The individually indefensible ones:

- INSTANCE carries no C++ data at all. Its own header says the exports object
  is an ordinary own property and the module reference is not stored. The
  cell kind is nothing but a brand.
- TAG heap-allocates a std::vector, and needs a finalizer, to hold a handful
  of enum values that would fit inline.
- MODULE needs its finalizer only for a unique_ptr. NativeState
  (include/hermes/VM/NativeState.h) is the existing mechanism for exactly
  that: a GCCell wrapping a native pointer plus a finalizer.

WHAT A CELL KIND BUYS, so a replacement does not lose it: an unforgeable
brand via dyn_vmcast, cheap and impossible to fake. The link paths depend on
it -- wasmLinkGlobal/Memory/Table are brand checks, and they are what
replaced the forgeable `__wasm_type__` string comparisons for those three
kinds. Any replacement must keep a brand that script cannot construct.
Internal properties give that too (script can neither name nor shadow them),
at the cost of a property read instead of a kind compare.

Candidate directions, none decided:
  (a) Instance loses its cell kind outright; it stores nothing.
  (b) Module keeps a brand but holds its native data in a NativeState rather
      than a bespoke finalizer.
  (c) Tag stores its parameters inline instead of in a std::vector, which
      also removes its finalizer.
  (d) The whole model collapses to ONE cell kind carrying a kind tag, so the
      brand is one class rather than seven.

NOT A COMPATIBILITY BREAK. CellKinds.def says it outright: cell kinds are
runtime-only, not encoded in bytecode, so renumbering or removing them costs
nothing on that axis. Note that sentence is about RENUMBERING being free; it
is not a licence to add them, which is how it got read at least once.

TIMING. The fix for 01a07f25-046f is about to route module-defined tags
through JSWebAssemblyTag rather than plain objects, because that class
already exists and the alternative was inventing a second tag-type mechanism
beside it. That INCREASES reliance on one of the seven. It is still the right
call for that issue -- it removes a forgeable string and a spec gap without
adding a cell kind -- but read this issue before unwinding it.
