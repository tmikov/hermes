Found 2026-09-06 while checking Wasm support from `hermes-node`
(hermes-node-compat, Hermes submodule at the `hermes-node` tip `96f7a4103`,
which merges this branch).

Every Wasm trap raises a plain `Error`. The spec says a trap surfaces in
JavaScript as a `WebAssembly.RuntimeError`, and the class exists here and is
otherwise correct -- it is just never the thing thrown.

## Measured

```
$ hermes-node wasm-real.js
FAIL unreachable traps: Error: unreachable executed
FAIL i32.div_s by zero traps: Error: integer divide by zero
FAIL bad call_indirect type traps: Error: call_indirect: undefined element
```

The messages are right; only the type is wrong. `e instanceof
WebAssembly.RuntimeError` is false, and `e.constructor.name` is `Error`.

## Cause

The trap builtins in `HermesBuiltin.cpp` all raise through
`Runtime::raiseError()`, which builds a plain `Error`:

```cpp
CallResult<HermesValue> wasmTrap(void *, Runtime &runtime) {
  return runtime.raiseError("unreachable executed");
}
```

21 builtins do this: `wasmTrap`, `wasmCallIndirect`, `wasmDataSegmentInit`,
`wasmI32DivS`/`DivU`/`RemS`/`RemU`, `wasmI64DivS`/`DivU`/`RemS`/`RemU`,
`wasmI32TruncF64S`/`F64U`, `wasmI64TruncF64S`/`F64U`, `wasmMemoryCopy`/`Fill`/
`Init`, `wasmTableCopySlots`/`Fill`/`Init`. So it is systematic rather than a
missed site.

## Why the conformance numbers do not show it

`run-spec-test.py`'s `assert_trap` generates a bare `catch(e) { passed++; }`
(`test/wasm/spec/run-spec-test.py:395-402`) -- any exception counts. So the
24,682 passing assertions say nothing about trap type, and neither does
`webassembly-errors.js`, which constructs a `RuntimeError` by hand and checks
its shape without ever provoking a real trap.

## Why it matters beyond conformance

Toolchain runtimes branch on it. emscripten's exception handling and
wasm-bindgen both distinguish "the module trapped" from "the JS glue threw" by
testing `instanceof WebAssembly.RuntimeError`, and a plain `Error` reads as the
second. A program that means to catch a trap and recover will instead either
swallow a real JS bug or rethrow its own trap.

## Suggested shape of the fix

`WebAssembly.cpp` already has `raiseCompileError` and `raiseLinkError`
(lines ~222-280), each building a `JSError` on the matching prototype;
`runtime.wasmRuntimeErrorPrototype` is right there beside the two they use.
The missing piece is a third such helper reachable from `HermesBuiltin.cpp`,
which is a different translation unit, so it needs to be declared somewhere
both can see rather than left `static`.
