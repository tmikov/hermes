The per-activation transport container for multi-value Wasm reference results is an ArrayStorage
carried in a HermesValue on the JS register stack, allocated and accessed through three private
builtins (wasmAllocRefBuf / wasmRefBufGet / wasmRefBufSet).

That works and is GC-correct: register roots are scanned (Runtime.cpp:603) and ArrayStorage's
metadata traces its elements (ArrayStorage.cpp:39). ArrayStorage::create already returns
HermesValue::encodeObjectValue, and PinnedValue<ArrayStorage> is routine elsewhere, so the cell
type in a HermesValue is not itself new.

WHAT IS NEW is that it becomes a bytecode register operand and a call argument, and
HermesValue::isObject() answers TRUE for it while it is not a JSObject. Any operation applied to
that register is type confusion -- an assert in Debug, a static_cast in Release. The hazardous
sequence already exists in the interpreter: isObject() followed by vmcast<JSObject> with no kind
check (Interpreter.cpp:1887 and 1964-1965).

Nothing enforces the boundary. The safety argument is that generated IR applies no operation to
the value and only the three builtins consume it -- true today, unenforced, and in tension with
the threat model the same change states for private builtins ("reachable from ANY bytecode that
emits a CallBuiltin with its index, so arguments cannot be taken on trust"). You cannot distrust
the arguments and vouch for the result. Reaching it needs hand-produced bytecode; ordinary JS
source cannot emit a private-builtin CallBuiltin.

Note also that IR type `any` does not help here: TypeContext.h:260 defines `any` as the union of
JS-OBSERVABLE types, not an opaque internal-cell type. It neither restricts consumers nor prevents
ordinary property operations.

TWO ALTERNATIVES, each identified independently by a reviewer, each avoiding the non-JSObject
representation:

  1. FastArray. It IS a JSObject (FastArray.h:21) holding its own ArrayStorageSmall, and
     AllocFastArrayInst / FastArrayStoreInst / FastArrayLoadInst are lowered by HBC ISel
     (lib/BCGen/HBC/ISel.cpp:2449-2492) with no IRVerifier type precondition
     (IRVerifier.cpp:1709-1723). This makes isObject() honest, removes all three builtins, and is
     cheaper per access than three CallBuiltins. Its residual hazard is the mirror image --
     FastArrayStore trusts its operand -- which the existing no-wasm-closure-escapes property
     already covers.

  2. An intrinsically allocated private JSArray, accessed exclusively through native own-storage
     operations and kept separate from the public result array. Avoids the non-JSObject
     representation without new tagging machinery, at an object-header cost.

  For stronger enforcement than either: an internal IR type with verified consumers.

Not done during the reference-types work because spec section 7 names ArrayStorage and native
builtins explicitly, and changing the representation mid-plan would have re-opened a contract that
took four review rounds to settle. The transport contract itself is independent of the
representation -- per-activation allocation, buffer identity for nested calls, caller-retained as a
local IR value -- so a representation swap does not disturb it.

    Sharper precedent, from review: the closest existing case is not PropertyAccessor but Environment
    in object-tagged registers (lib/VM/Interpreter.cpp:1716). Environment likewise rides a register as
    a non-JSObject cell -- but it HAS A DISTINCT IR TYPE, which is precisely what the transport value
    lacks. That makes Environment the model to copy if the representation stays, and the gap between
    them the concrete statement of what is missing.

    So the options, ordered by how much they change:

      a. Give the transport value its own IR type with verified consumers. Closest to Environment,
         keeps ArrayStorage, and turns the containment argument into something the verifier enforces
         rather than something a comment asserts.
      b. FastArray -- a real JSObject, existing lowered IR instructions, removes all three builtins,
         cheaper per access than three CallBuiltins.
      c. An intrinsically allocated private JSArray accessed through native own-storage operations.

    Also recorded so nobody re-derives it: the "this is new for the cell type" framing was wrong.
    ArrayStorage::create already returns encodeObjectValue and PinnedValue<ArrayStorage> is routine.
    What is new is only that the value becomes a BYTECODE REGISTER OPERAND AND CALL ARGUMENT.
