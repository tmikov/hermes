Recorded as **H17** in the Wasm branch review (`wasm-old-rebased`). Pre-existing.

## Status correction

The ledger briefly recorded this as "CLOSED by construction" after the §4.4
internal-slots pass. **That overstated it**, and the source comment written by
that same pass already said so: `HermesBuiltin.cpp` notes that `getNumber()`
"is NOT guaranteed on an externref table reached by an invalid module."

What §4.4 closed is the **forging route** — `__wasm_types__` is no longer a
published, writable property, so script can no longer seed the types array
directly. The **unchecked read survives**.

## The surviving defect

`wasmCallIndirect` does `truncateToInt32(typeVal.unboxToHV(runtime).getNumber())`,
assuming the types array holds numbers. An externref table's three arrays are
still three independent `new Array(n)` calls off a replaceable
`globalThis.Array`, and `wasmCheckTableArrays` validates array-*ness* only, never
contents. Reproduced at HEAD via `wat2wasm --no-check` plus a replaced `Array`
seeding `{}`:

```
hermes: HermesValue.h:383: Assertion `isDouble()' failed.
```

In Release that reads object bits as a double.

## Relationship to other issues

Reaching it requires an invalid module, so it sits behind **H19**
(`hermesc --wasm` does not validate). Fixing H19 closes this by construction; a
contents check on the read would close it independently.

`e2e-table-import-hostile.wat`'s `types=objects` row pins the **brand check**, not
this read — its header says so honestly. Do not read that row as coverage for
this.

    ## Status update: H19 is fixed, so this issue's "Relationship" section is stale

    This issue says:

    > Reaching it requires an invalid module, so it sits behind **H19**
    > (`hermes --wasm` does not validate). Fixing H19 closes this by
    > construction; a contents check on the read would close it independently.

    H19 is now closed. Both compile entry points validate, so **no invalid module
    can be compiled by this engine any more** -- `wat2wasm --no-check` output is
    refused by `hermesc --wasm` exactly as it already was by
    `new WebAssembly.Module`.

    But "closes this by construction" is only half right, and the half that is
    wrong is the half that matters:

    - **The COMPILE route is closed.** You can no longer produce the `.hbc` that
      reaches the unchecked read.
    - **The READ is unchanged.** `wasmCallIndirect` still does
      `truncateToInt32(typeVal.unboxToHV(runtime).getNumber())` with no check
      that the slot holds a number.
    - **`.hbc` is trusted by design on this branch.** Bytecode compiled by an
      engine built BEFORE this fix -- or by any other producer -- still reaches
      the read. The fix removed the way to make new bad bytecode; it did not add
      a check, and it cannot reach bytecode that already exists.

    So this stays open, and the remaining fix is the one this issue already
    names: a contents check on the read, or a decision that trusted `.hbc` makes
    it acceptable. The comment at the read was updated by the H19 commit and now
    states this correctly -- it keeps the check and says a fact about the caller
    is not a substitute for the value in hand.
