Found 2026-09-07 while planning `01a079c6-fdd6`, then measured.

A module that DEFINES and EXPORTS an `externref` table builds the exported
`WebAssembly.Table` by reading `globalThis.WebAssembly.Table` and calling it,
publishing whatever comes back unchecked. Script can replace that function
before instantiation and decide what the module's table export IS.

## Reproducer

```wat
(module (table (export "t") 1 externref))
```

```js
// 0,97,115,109,1,0,0,0,4,4,1,111,0,1,7,5,1,1,116,1,0
var mod = new WebAssembly.Module(bytes);          // compiled before the swap
var real = WebAssembly.Table;
WebAssembly.Table = function FakeT(){ this.hijacked = true; };
var e = new WebAssembly.Instance(mod).exports;
WebAssembly.Table = real;
print(e.t.hijacked === true, e.t instanceof real);
```

```
                              Hermes            Node v24.13.1
externref table export:       HIJACKED          genuine Table
funcref   table export:       LinkError         genuine Table
memory    export:             LinkError         genuine Memory
```

Hermes's messages on the two that do check:

```
LinkError: WebAssembly.Table did not construct a table for this module's table 0
LinkError: WebAssembly.Memory did not construct a memory for this module's memory 0
```

## Mechanism

A defined memory and a defined FUNCREF table are constructed and
brand-checked early (`WasmIRGen.cpp:5929` and `7049`), and their export loops
republish the already-checked object. The externref table export is a
separate fallback in the export loop that loads the constructor off the
global object and publishes its result with no check
(`WasmIRGen.cpp:2250`, `2274`).

Same class as the global export hole (fixed under `01a079c6-fdd6` by moving
construction into a builtin), as H2 (user JS reachable from inside
instantiation), and as the retired `__wasm_type__` forgery.

## Note on the fix

A brand check on the returned object is NOT sufficient on its own here for
the same reason it was not for globals: a replacement constructor can return
a genuine `WebAssembly.Table` unrelated to this module's storage, and can run
arbitrary code before returning or throwing. Construct internally, or check
the object AND that the module's own storage is the one it wraps.

Externref table IMPORTS separately cannot link at all today, so the import
side of this is unreachable rather than correct.
