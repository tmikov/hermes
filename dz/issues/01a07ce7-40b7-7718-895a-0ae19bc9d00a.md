Found 2026-09-07 while fixing H19 (`01a0460b-1ea9`). The finding was buried in
H19's prose, described there as one of its own failure modes; it is neither
H19 nor H17 and had no issue of its own.

`wasmCallIndirect` ends with:

```cpp
  return funcVal.unboxToHV(runtime);
```

There is **no brand check on that value**. It is read straight out of the
table's funcs array and handed back to generated IR, which calls it with the
INTERNAL calling convention -- the one that expects a Wasm closure, not a JS
function.

Every other check in that function guards a different thing:

- the bounds check guards the index
- the null/empty check traps an uninitialized element
- the type check compares the TYPES array entry against the expected id

None of them says the funcs entry is a Wasm function.

## How a bad value gets in

Same route as H17, one array over. `wasmCheckTableArrays`
(`HermesBuiltin.cpp:2160-2171`) validates that all three of a table's
backing stores are `JSArray`s -- **array-ness only, never contents**. For an
EXTERNREF table those three arrays come from three `new Array(n)` calls off a
replaceable `globalThis.Array`, so script chooses their contents.

A valid module cannot `call_indirect` through an externref table, so this
needs an invalid module -- which is exactly what H19 was about. Reaching it
therefore takes: seed the types array with a NUMBER (not an object, which
is H17's cruder crash), guess the interned type id so the type check passes,
and put a plain JS function in the funcs array at the same index.

## Why this is worse than H17

H17's unchecked read misreads object bits as a double -- an assert in Debug,
a garbage number in Release. This one **calls an arbitrary script-supplied
function with the internal Wasm calling convention**. That is type-confused
control flow, not a bad number.

## Current reachability, after H19

H19's fix means neither compile entry point will accept the invalid module
this needs, so it cannot be reached by compiling new bytecode. It remains
reachable through `.hbc` produced before that fix, or by any other producer;
`.hbc` is trusted by design on this branch, so this is a robustness and
toolchain-correctness issue rather than a hostile-script hole -- the same
severity framing H19 itself used.

## Fix

A `dyn_vmcast` on the funcs entry before returning it -- the same brand the
rest of the engine uses for an Exported Function (`isWasmExportedFunction`
/ `readWasmFuncInfo`). The objection raised for H17's read applies here too
(a branch on the indirect-call hot path), but the consequences are not
comparable: a wrong number versus entering arbitrary JS with the wrong
convention. If the branch is genuinely unaffordable, the alternative is to
stop letting script choose an externref table's backing arrays at all, which
would close H17 and this together.
