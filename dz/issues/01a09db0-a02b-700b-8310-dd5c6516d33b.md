Found 2026-09-14 by external review, after module-defined tags became
JSWebAssemblyTag cells and `new WebAssembly.Exception(moduleTag, payload)`
became constructible for the first time.

THERE ARE TWO REPRESENTATIONS OF A WASM EXCEPTION AND THEY DO NOT MEET.

  - Wasm's own: a JS Array, `[tag, ...payload]`. onThrow builds it,
    wasmMatchException recognises it by reading element 0 and comparing tag
    identity, and the handler unpacks the rest onto the Wasm stack.
  - The JS API's: a JSWebAssemblyException cell, holding the tag and the
    payload in private fields. `new WebAssembly.Exception(...)` builds it and
    `.is()` / `.getArg()` read it.

So an exception built through the JS API on a module's OWN tag, thrown into
that module's `try` with a matching `catch`, is not caught. It escapes to the
caller unchanged. Pinned as current behaviour by
test/wasm/e2e-catch-non-array.wat, which says there what it is.

The two also disagree about shape, not only about the container: the JS API
stores one payload entry per parameter, while the Wasm side splits an i64 into
two stack slots.

RECOMMENDED DIRECTION, from the reviewer and not yet weighed against the
alternative: make the CELL canonical. It already holds the tag and payload
privately and the JS API already consumes it, whereas the array publishes both
to script -- identity and payload storage are mutable by anyone holding the
thrown value, which is its own defect. That means coordinating onThrow,
onCatch, wasmMatchException and wasmCreateException together, and deciding
explicitly what an i64 payload entry looks like on both sides. Recognising the
cell in the matcher alone would not finish it.

NOT urgent, and note what it is NOT: it is not the unchecked cast that
test/wasm/e2e-catch-non-array.wat was written for -- that was
`vmcast_or_null<JSArray>` asserting instead of testing, and is fixed. This is
the representation gap underneath it.

Related: 01a0460b-abb6 (H21), exception payloads as an unvalidated inbound
boundary.
