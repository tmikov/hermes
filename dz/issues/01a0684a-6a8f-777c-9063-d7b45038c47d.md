Recorded limitation, not a defect: correctness was the goal and is
established. This documents what the JIT can and cannot do for
wasm-generated code today, with measurements and disassembly, so the
performance work has a concrete starting point.

## Baseline facts (measured 2026-09-03, wasm-test-jit merge branch =
## wasm-new + x86-jit, x86-64)

The JIT fully supports wasm-generated code: every wasm function
compiles (65/65 in call.wast alone), and the entire spec suite passes
under `-Xjit=force` with `-Xjit-crash-on-error`, where an unsupported
instruction would be a hermes_fatal — so the clean sweep proves
complete instruction coverage, not just absence of observed bails.
Results are identical across no-JIT, threshold JIT, and force
(62/83 files, 24682/120 assertions, the documented conformance level).

## Measurements

Release/clang HV64 build (`-DHERMESVM_ALLOW_JIT=2
-DHERMES_ENABLE_WASM=ON`), five .wat microbenchmarks compiled with
wabt's wat2wasm, loaded via WebAssembly.Module/Instance from a JS
driver, timed in-process around the hot exported function only
(Date.now around `run(N)` after a warmup call), JIT as
`-Xjit -Xjit-threshold=0 -Xjit-crash-on-error`, 5-rep interleaved
medians, quiet machine:

    bench  shape                interp    jit   jit/interp
    fib    recursive calls      1949ms   802ms    2.43x
    f64    f64 mul/add loop     1594ms   822ms    1.94x
    mem    i32.store/load loop  2065ms  1695ms    1.22x
    arith  i32 mul/xor/shift    2001ms  1699ms    1.18x
    i64    i64 LCG loop         2026ms  1799ms    1.13x

The JIT wins where JS and wasm semantics coincide (calls, f64). It
barely moves i32 arithmetic, memory access, and i64.

## Why, from the emitted code

Disassembly of the arith hot loop (`-Xdump-jitcode=3`, function
`wasm_export_run`), per iteration:

- `i32.mul` lowers to `CallBuiltin Math.imul`, which the JIT emits as
  a full `_jit_call_builtin` C++ call: frame syncs of the operands,
  all temp registers freed, call, result reloaded. One helper call
  per wasm multiply.
- `i32.shr_u` (and every bitwise op) pays the JS double->int32
  conversion dance on BOTH operands: vcvttsd2si + vcvtsi2sd +
  vucomisd + two conditional branches to a slow path (the exactness
  check), then the 32-bit `shr`, then vcvtsi2sd to box the result
  back into a double. The value never stays an integer.
- Values ping-pong between GP and XMM registers accordingly.

The interpreter pays the same conversions plus dispatch; the JIT
removes only the dispatch, hence ~1.2x. This is a lowering property,
not a JIT deficiency: the IR the backend receives is JS-number IR.

Not disassembled but following from the lowering:

- mem (1.22x): i32.load/store become typed-array element accesses on
  the HEAP views with double-typed indices — per access, index
  conversion plus the typed-array checks, in both engines' tiers.
- i64 (1.13x): every i64 arithmetic op is a CallBuiltin
  (HermesBuiltin_wasmI64Mul etc., WasmHelpers.cpp), i.e. a C++ helper
  call per operation under the JIT as well. Note these do NOT appear
  in `-Xjit-emit-counters` NumCall/NumCallSlow — those counters track
  Call instructions only, CallBuiltin is uncounted, which briefly
  misled the investigation.
- fib's residual gap after 2.43x is the JS calling convention (frame
  setup, register-stack traffic), which wasm-to-wasm calls do not
  semantically need.

## What faster wasm would take (directions, not commitments)

JIT tuning cannot fix this; the information is destroyed before the
backend sees it. In rough order of leverage:

1. Int32-typed values in the IR, carried through bytecode to the JIT
   frame-register types, so the backend can keep wasm i32 values in
   integer registers and emit imul/shr/and directly. The verified-i32
   invariant already exists semantically in wasm; the pipeline just
   cannot express it.
2. Dedicated memory-access instructions (int index, no
   detach/bounds re-derivation per access) — the same VM-level work
   doc/WasmSpecTestStatus.md already flags for making bounds checking
   affordable outside --test262.
3. i64 representation that is not one C++ call per op (register
   pairs or native i64 slots).
4. A cheaper call sequence for known wasm-to-wasm calls.

## Repro

arith.wat, representative of the i32 findings:

    (module
      (func (export "run") (param $iters i32) (result i32)
        (local $acc i32) (local $i i32)
        (block $done
          (loop $l
            (br_if $done (i32.ge_s (local.get $i) (local.get $iters)))
            (local.set $acc
              (i32.xor
                (i32.add (i32.mul (local.get $acc) (i32.const 3))
                         (local.get $i))
                (i32.shr_u (local.get $acc) (i32.const 5))))
            (local.set $i (i32.add (local.get $i) (i32.const 1)))
            (br $l)))
        (local.get $acc)))

Driver: load bytes with hermescli.loadFile (needs
-Xhermes-internal-test-methods), new WebAssembly.Module/Instance, warm
run(N/10), time run(80000000). fib used fib(27) x 150 iters; mem
walked a 64KB page with i32.store then i32.load, 3000 iters; f64
mul/add x 150e6; i64 LCG x 40e6. Interp/JIT results bit-identical on
every bench (also verified on the ASan tree under force).
