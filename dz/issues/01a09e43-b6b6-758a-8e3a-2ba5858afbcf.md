Found 2026-09-14 by external review of the export-publication fix.

Exporting an externref table normally fails: createTables() builds a
descriptor with element "externref", and WebAssembly.Table's constructor
accepts only "anyfunc"/"funcref", so instantiation raises a TypeError. The
comment at that site says so.

The element type reaches the constructor through an ORDINARY property store on
a fresh object literal, so it walks the prototype chain. An accessor on
Object.prototype named `element` whose setter swallows the store and whose
getter answers "anyfunc" changes the outcome completely:

  honest:                TypeError
  with element hijacked: linked; t is a Table: true, length 1

So the module links, and exports a genuine funcref WebAssembly.Table for a
table it declared as externref. That object's storage is its own -- the
module's externref table is three plain arrays in its own scope -- so the
exported table and the module's table are unrelated: writes through
exports.t.set() are invisible to the module, and table.get inside the module
never sees them.

Not fixed with the rest of the publication work, because the fix interacts
with a decision that is still open. Converting the CONSTRUCTOR DESCRIPTORS to
DefineOwnPropertyInst would close the setter half here, but not the getter
half: a descriptor omits `maximum` when the module declares none, and an
inherited getter then supplies one with nothing to overwrite. Measured
separately on `(memory 1)`: an Object.prototype `maximum` getter returning 2
still reaches the constructor and is caught by the exact-limits check. So
closing descriptor interference properly means either giving the descriptor a
null prototype or having the constructors stop consulting inherited
properties, and that decision also governs whether the exact-limits checks in
createMemoryViews()/createTables() stay reachable.

The narrower fix available today is the compile-time diagnostic the comment
already contemplates: refuse a module that exports an externref table, the way
validateTagTypes() refuses a v128 tag parameter. That removes the path
entirely rather than hardening it.
