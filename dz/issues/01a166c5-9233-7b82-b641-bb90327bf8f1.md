Wasm i32 values live in Hermes registers as doubles. The only numeric-typed
opcodes are `AddN`/`SubN`/`MulN`/`DivN` and the `JLessN` family. Shifts,
bitwise ops, `ToInt32`/`ToUint32` and strict equality only exist in their
generic JS form, so every one the Wasm frontend emits carries conversions,
tag tests and a slow path in the JIT. This is a fix in the Wasm frontend and
the bytecode, not a JIT heuristic.

Sibling: 01a166c5-920c (Wasm memory access should be typed in the bytecode).
Umbrella: 01a0684a-6a8f (typed IR for wasm-competitive codegen), item 1.
Measurements: hermes-node dz 01a14270-48bc, section "Where the code size
comes from".

## What the JIT emits

Measured by the hermes-node session on Linux x86-64 Release, at the
hermes-node gitlink, on hermes-parser's 768,303-byte parser.wasm. It
reassembled the `-Xdump-jitcode=1` listing of every compiled version with
llvm-mc and attributed every byte to the op, tier, sync or slow path that
emitted it. Totals land 7.5% under the JIT's own figures because llvm-mc
picks short jumps; the shares are unaffected.

All Wasm functions, version 1: 105,959 bytecode instructions -> 11.0 MB.

| op | % of instructions | % of bytes | bytes each |
| --- | --- | --- | --- |
| shifts/bitwise + slow paths | ~12% | ~16% | ~132 |
| JStrictEqual + its slow path | 6.8% | 12.2% | ~188 |
| ToInt32/ToUint32 + slow paths | 5.1% | 4.4% | ~88 |
| AddN (for contrast) | 15.3% | 2.6% | 18 |
| Mov (for contrast) | 12.7% | 1.2% | 10 |

Each JIT emit of `URshift`/`LShift`/`RShift`/`BitAnd`/`BitOr`/`BitXor`:

- converts EACH operand double -> int64 with a round-trip exactness check
  (vcvttsd2si, vcvtsi2sd, vucomisd, jne/jp);
- does the op;
- converts the result back to double;
- carries a slow path calling the generic helper, e.g.
  `_sh_ljs_unsigned_right_shift_rjs`.

That is ~132 bytes per op, 72 inline + 53 slow. `ToInt32` is 44 bytes inline
+ 44 slow. `AddN` is 18 bytes because it is typed.

`addr >>> 2` is emitted for every aligned 32-bit memory access. The constant
2 is materialized into a register (`LoadConstUInt8`) and then goes through
the same exactness check as a variable operand, because it arrives as a
register. Bytecode reproduced in 01a166c5-920c.

The OOB `=== undefined` after each load compiles to the fully generic strict
equality: about 40 instructions plus a 57-byte slow path (a double compare,
NaN-box tag tests, a string-compare path). Most of that 12.2% is those OOB
checks, which 01a166c5-920c would remove. Real Wasm `i32.eq` etc. would remain.

## Why bytecode selection does not use the IR types

The Wasm frontend types its results: lib/WasmIRGen/WasmIRGen.cpp calls
`setType(Type::createNumber())` 87 times, including on the shift results.
But:

- `HBCISel::generateBinaryOperatorInst` (lib/BCGen/HBC/ISel.cpp:890)
  computes `isBothNumber` and uses it only for `+ - * /`, choosing
  `AddN`/`SubN`/`MulN`/`DivN`. The compare-branch path (:1647) uses it only
  for the `<`/`<=`/`>`/`>=` family. Shifts, bitwise ops and `===`/`!==`
  always emit the generic opcode, because there is no typed opcode to pick.
- The IR has no int32 type. `Type` stops at number, so the most the frontend
  can state about a Wasm i32 is "number" (WasmIRGen.cpp creates no int32
  type anywhere). "Both operands are numbers" would remove the non-number
  slow path from a shift. Dropping the double <-> int conversions as well
  needs the IR, and then the bytecode, to say "int32".

## Direction

- Number- or int32-typed opcodes for shifts, bitwise ops and equality. Their
  operands are known numbers, so no conversion checks against non-numbers
  and no generic slow path. With int32 operands, no exactness check either.
- Immediate shift counts (a shift-by-constant form), so `>>> 2` needs no
  register constant and no conversion of the count.
- Possibly keep i32 values unboxed as int32 in the JIT. That is umbrella
  01a0684a-6a8f item 1.
- `ToInt32`/`ToUint32` of a known number is a pure truncation and needs no
  generic slow path.

## Versioning

- Changing the opcodes the Wasm frontend selects changes the bytecode
  produced from identical input, so `WASM_CODEGEN_VERSION`
  (include/hermes/WasmFrontend/WasmCodegenVersion.h) must be bumped. That
  header comes from the wasm-module-cache branch and is not on wasm-new yet.
  Bump it wherever the header exists when this lands.
- New opcodes are a bytecode format change. That is covered by the
  release-time BYTECODE_VERSION bump, not a per-change one.
