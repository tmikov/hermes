Found 2026-09-07 by external review of the H19 fix (`01a0460b-1ea9`). NOT
caused by that fix -- the JS path has always validated and has always
rejected this -- but the fix made `hermesc --wasm` agree, so it is now the
behaviour on both entry points and is worth recording.

Hermes refuses a module that is valid under the current Wasm specification:
a global whose initializer reads a PRECEDING IMMUTABLE global.

## Reproducer

```wat
(module
  (global $a i32 (i32.const 7))
  (global (export "b") i32 (global.get $a)))
```

```
node   -> WebAssembly.validate: true; instantiates; exports.b.value === 7
hermes -> WebAssembly.validate: false
          new WebAssembly.Module: <validate>:0000014: error: initializer
          expression can only reference an imported global
hermesc --wasm -> same message, rc=2
```

`wat2wasm` itself refuses to emit it without `--no-check`, for the same
reason: the vendored wabt shares the restriction.

## Cause

`SharedValidator::OnGlobalGet` (`external/wabt/wabt/src/shared-validator.cc:
863-878`) errors whenever an init expression names a global whose index is
`>= num_imported_globals_`:

```cpp
  if (Succeeded(result) && in_init_expr_) {
    if (global_var.index() >= num_imported_globals_) {
      result |= PrintError(
          global_var.loc,
          "initializer expression can only reference an imported global");
```

That is the pre-2.0 rule. The current spec allows a constant expression to
reference any preceding immutable global, imported or not.

The check is **unconditional** -- not gated on any entry in
`external/wabt/wabt/include/wabt/feature.def`. Enabling `extended_const`
does not lift it, and neither would `gc`. So this is not fixable by adding a
feature bit to `wasmFeatures()`; it needs the vendored wabt updated or the
check patched.

## Hermes itself already supports the construct

This is the frustrating part: nothing in Hermes needs the restriction. The
IRGen implements exactly this copy -- `WasmGlobal::InitKind::GlobalGet` in
`initializeGlobals` (`lib/WasmIRGen/WasmIRGen.cpp`, the GlobalGet arm) loads
the source global's slot and stores it into the target's, and asserts
`srcIdx < globalIdx`, which is precisely the spec's "preceding" rule. Only
the validator objects.

## Severity

Low frequency, silent-free: the module is refused with a clear message, so
nothing miscompiles. But it is a real spec-conformance gap -- Hermes says
`WebAssembly.validate` is false for a module every other engine accepts, and
a toolchain emitting this pattern cannot target Hermes at all.

## Fix options

1. Update the vendored wabt to a revision where the restriction follows the
   current spec. Cleanest, largest blast radius.
2. Patch the check in the vendored copy to allow a preceding immutable
   global. Small and targeted; adds a local delta to a vendored tree.
3. Accept and document the limitation.

## Related
