The inline PutById path in JIT code handles only a store to a property
the object already has (the write cache's `clazz` matches). A store that
adds a property always calls `_jit_put_by_id`
(lib/VM/JIT/JitHandlers.cpp). The helper has a cache for it:
`AddPropertyCacheEntry` (include/hermes/VM/PropertyCache.h), checked on
start class, live result class, parent epoch and parent, then
`JSObject::addNewOwnPropertyInSlot` with the cached class and slot. So
the cache exists; what costs is leaving JIT code for every add.

The helper also counts each call as a decline of the calling body before
it checks either cache, so a site whose add cache always hits still
drives `considerRecompile`. Whether that triggers recompiles that cannot
help has not been checked.

Current profile, HV64 x86-64 Release at 7357a443f, `-Xjit`, from
bytecode, share of all samples:

| bench | _jit_put_by_id | addNewOwnPropertyInSlot | considerRecompile |
|---|---|---|---|
| RayTrace | 11.4 | 4.8 | 0.9 |
| Earley-Boyer | 8.1 | 3.1 | 0.6 |
| TypeScript | 3.9 | 1.7 | 1.4 |
| DeltaBlue | 1.8 | 0.9 | 0.4 |

`_jit_put_by_id` self time also covers sites that miss for other
reasons (polymorphic existing-property stores). Split the add hits from
those with counters before building anything. An inline add can only
cover the case where the slot already has room: direct slots, or
indirect storage with spare capacity; growing the storage allocates and
stays in the helper.
