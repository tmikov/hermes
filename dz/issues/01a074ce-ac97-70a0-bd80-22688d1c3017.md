Found 2026-09-06 while checking Wasm support from `hermes-node`
(hermes-node-compat, Hermes submodule at the `hermes-node` tip `96f7a4103`,
which merges this branch). Not from a review pass -- found by running the
compiler over Node's own `.wasm` test fixtures.

A module that exports a **global** whose type is `externref`, `funcref` or
`v128` reaches `finalizeModule()`'s type-descriptor switch
(`WasmIRGen.cpp:2124-2140`), which has arms for only I32/I64/F32/F64 and a
`default:` of `llvm_unreachable("unsupported global export type")`. Under
NDEBUG that is `__builtin_unreachable()`, so the process walks off the end of
the switch.

## Reproducer

One line of WAT:

```wat
(module (global (export "g") externref (ref.null extern)))
```

```
$ wat2wasm --enable-all gextref.wat -o gextref.wasm
$ cmake-build-release/bin/hermesc --wasm -dump-ir gextref.wasm
Segmentation fault (core dumped)     # rc=139
```

Identical for `funcref` (`(ref.null func)`) and `v128`
(`(v128.const i32x4 1 2 3 4)`).

Measured in three configurations of this tree at `97fd37a08`:

| build | result |
|---|---|
| `cmake-build-release` (NDEBUG), rebuilt for this | SIGSEGV, rc=139 |
| `cmake-build-asan` (assertions) | `UNREACHABLE executed at WasmIRGen.cpp:2139!`, rc=134 |
| hermes-node-compat `cmake-build-wasm` (RelWithDebInfo) | SIGSEGV |

(`cmake-build-debug/bin/hermesc` exits 0 on it, but that binary is from
Jul 28 and predates this code -- not a counterexample.)

## It is reachable from JavaScript, and `validate()` does not screen it

```
$ hermes-node -e '
  const b = require("fs").readFileSync("gextref.wasm");
  console.log("validate:", WebAssembly.validate(b));
  try { new WebAssembly.Module(b); } catch (e) { console.log("caught:", e.message); }
  console.log("survived");'
validate: true
Segmentation fault (core dumped)
```

So a host that does the defensive thing -- validate untrusted bytes, then
compile inside a try/catch -- still dies. The module is genuinely valid:
`WebAssembly.validate` runs the real thing (`validateWasmBinary` ->
`wabt::ValidateModule`, `WasmCompile.cpp:167-183`) and accepts it, because
reference-typed globals are standard Wasm 2.0.

## Not H19

H19 is "`hermesc --wasm` does not validate the module", and the comment above
these very export loops (`WasmIRGen.cpp:1693-1706`) describes fixing an
out-of-bounds read on a **malformed** module whose export index had been
patched by hand. This is the opposite case: the module is well-formed and
valid, and the crash is a missing switch arm rather than an unchecked index.
Fixing H19 would not fix this.

## Scope

Only the global-**export** path. Importing a reference-typed global, and
using one inside the module, both compile fine:

```wat
(module (import "e" "g" (global externref)))                          ;; rc=0
(module (import "e" "g" (global $g externref))
        (func (export "f") (result externref) (global.get $g)))       ;; rc=0
```

Unsupported *opcodes* already degrade gracefully -- `resources/wasm-js-cycle.wasm`
prints `warning: unsupported Wasm opcode: ref.func` and carries on. This path
is the one place that aborts instead.

## Node fixtures that hit it

```
/home/tmikov/3rd/node/test/fixtures/es-modules/dep.wasm       (12 exported globals: i32/i64/f32/f64/externref/v128)
/home/tmikov/3rd/node/test/fixtures/es-modules/globals.wasm   (35 exported globals, same spread)
```

They are the only 2 of 42 Node `.wasm` fixtures that crash; the other 40
compile, and 12 of those instantiate and run.

## Suggested shape of the fix

`finalizeModule()` already returns `bool` and reports through `errorMsg_`,
which is how `validateExportIndices()` (`WasmIRGen.cpp:1648-1686`) rejects a
bad export. Setting `errorMsg_` to something like
`export "g" has type externref, which is not supported` and returning false
would turn all three cases into a `CompileError`, catchable and truthful,
with no new mechanism. Whether reference-typed global exports should later be
*supported* is a separate question -- exporting them as
`WebAssembly.Global` objects needs `JSWebAssemblyGlobal` to hold a reference
value, which is a feature, not a bug fix.

    ## Investigation 2026-09-06 (this tree, `b09d3dbac`)

    ### Reproduced, and reachable without `hermes-node`

    The report demonstrates JS reachability through `hermes-node`. It reproduces
    in this worktree's own `hermes` binary, no submodule involved. The module is
    23 bytes and can be written inline, so the repro needs no `wat2wasm`:

    ```js
    // (module (global (export "g") externref (ref.null extern)))
    var b = new Uint8Array(
        [0,97,115,109,1,0,0,0,6,6,1,111,0,208,111,11,7,5,1,1,103,3,0]);
    print("validate:", WebAssembly.validate(b));
    try { new WebAssembly.Module(b); } catch (e) { print("caught:", e.message); }
    print("survived");
    ```

    ```
    $ cmake-build-asan/bin/hermes t.js
    validate: true
    unsupported global export type
    UNREACHABLE executed at lib/WasmIRGen/WasmIRGen.cpp:2139!    # rc=134
    ```

    `funcref` (`0x70` / `0xD0 0x70`) and `v128` are identical. `hermesc --wasm`
    dies on `-emit-binary` as well as on `-dump-ir`, so it is not a dump-path
    artifact. The switch is the ONLY `llvm_unreachable` in `lib/WasmFrontend/`
    and `lib/WasmIRGen/` combined.

    ### The missing arm is a symptom; the runtime cannot hold the value

    Adding a fifth arm to `WasmIRGen.cpp:2125-2140` on its own does not fix
    this. It replaces the abort with a wrong exception thrown from inside
    instantiation, because there is no such thing as a reference-typed
    `WebAssembly.Global` in this VM:

    - `JSWebAssemblyGlobal` stores a `double value_` and an `int64_t i64Value_`
      (`include/hermes/VM/JSWebAssemblyGlobal.h:114,119`). There is no
      GC-visible slot a reference could live in.
    - `ValType` is `{I32,I64,F32,F64}` and its numeric values are an ABI, baked
      into `WasmIRGen::globalValTypeCode` (`WasmIRGen.cpp:77-85`) and held there
      by `static_assert`.
    - `wasmGlobalConstructor` accepts only `"i32"/"i64"/"f32"/"f64"`
      (`WebAssembly.cpp:2185-2197`); anything else is a TypeError.

    So the IRGen half of a real fix is three lines and the runtime half is a
    cell-layout change.

    The comment at `WasmIRGen.cpp:411-417` already describes this abort and says
    it "is recorded as a separate defect" -- this issue is that record.

    ### Adjacent defect found while examining: ref-typed global IMPORTS never link

    The report says importing a reference-typed global "compiles fine". True of
    `hermesc`, not of running it. A module importing `(global externref)` and
    returning it from an exported function:

    ```
    caught: LinkError: import e.g must be a Number to satisfy an externref global import
    ```

    Node links the same bytes and round-trips object identity
    (`i.exports.f() === obj` is `true`).

    Two causes, both on the same path. `globalValTypeCode` returns `0xFF` for
    every reference type, so `wasmLinkGlobal` matches no `WebAssembly.Global`
    at all; and the raw-value fallback then demands `typeof === "number"` for
    everything that is not i64 (`WasmIRGen.cpp:1019-1052`, `1080-1096`). Per
    spec an externref import takes ANY JS value and a funcref import takes null
    or an Exported Function. The message is self-contradictory as written.

    This is not the crash and should probably be its own issue.

    ### v128 is a different problem from the two reference types

    Measured against Node for what correct behavior actually is:

    | case | Node | this tree |
    |---|---|---|
    | exported `externref` global | `Global`, `.value === null` | crash |
    | exported `funcref` global | `Global`, `.value === null` | crash |
    | exported `v128` global | `Global`, `.value` throws TypeError | crash |
    | `new WebAssembly.Global({value:"v128"})` | TypeError | TypeError, by accident |
    | `new WebAssembly.Global({value:"anyfunc"})` | ok, `null` | TypeError |
    | `new WebAssembly.Global({value:"funcref"})` | TypeError | TypeError |

    A v128 global is never readable from JS by design: the JS API's
    `ToValueType` has no `v128`, and the `.value` getter throws for it. Note
    also that the descriptor spelling for a funcref global is `"anyfunc"`, not
    `"funcref"`.

    Separately, `BinaryReaderHermesIRGen` has no `v128.const` init handler at
    all, so a v128 global falls through to the default `InitKind::I32Const`
    with `initValue` default-constructed to 0 and its slot silently initializes
    to the number `0`. Consistent with v128 being unsupported project-wide
    (SIMD opcodes warn and continue), and an argument against implementing
    v128 globals rather than for it.

    ### Shape of a fix

    1. **Diagnose instead of abort.** Set `errorMsg_` and `return false`; the
       crash becomes a CompileError. Small and self-contained, but rejects
       valid Wasm 2.0 modules, including both Node fixtures.
    2. **Support externref/funcref properly.** A GC-visible value slot on
       `JSWebAssemblyGlobal` (cell layout, metadata, snapshot); two new
       `ValType` codes with their `static_assert`s and `globalValTypeCode`;
       `"externref"` and `"anyfunc"` in the constructor; a funcref brand check
       in the `.value` setter; `wasmLinkGlobal` matching plus the raw-import
       path, which also closes the import defect above; then the IRGen arm.
    3. **v128: diagnose, do not implement.** Even the spec's answer is a
       `Global` whose `.value` throws.

    Suggested: 2 for the two reference types, 1 for v128.

    Regression tests go in `test/wasm/` as `.wat`; `wat2wasm` is built in tree
    at `<build>/external/wabt/wabt/wat2wasm` and substituted by `test/lit.cfg`.
