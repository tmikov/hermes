Five heap-use-after-frees were found and fixed in lib/VM/JSLib/WebAssembly/WebAssembly.cpp
during the reference-types work (commits 87ca2bd55 and 3bf1a1524 on branch wasm-new). All five
were the same pattern: a raw GC pointer -- a StringPrimitive*, a JSWebAssemblyTag*, a
JSWebAssemblyException*, or a reference to a std::vector member living inside a movable cell --
held across an allocating call and dereferenced afterwards. All five were reachable from the
public JS API:

  - wasmGlobalConstructor, the type-name parser
  - wasmTableConstructor, the element-type comparison
  - parseValTypeString, called from wasmTagConstructor
  - wasmExceptionConstructor, `const std::vector<ValType> &` bound into the Tag cell and
    indexed after getComputed_RJS and toNumber_RJS
  - wasmExceptionGetArgMethod, raw exc and tag held across a toNumber_RJS that runs a user
    valueOf

What is NOT done: the fixes followed the pattern through the JS-API constructors and
accessors only. The instantiate and link paths in the same file -- substantially larger, and
the ones the reference-types work adds further allocating calls to -- were not audited.

Why this stayed hidden: cmake-build-sanhandles samples at 1% by default, so a green
LIT_FILTER="wasm" run in that build sat over all five live bugs for as long as they existed. A
test only exercises this reliably if it passes -gc-sanitize-handles=1 explicitly. Any audit
should account for that, or it will report clean for the same reason.

Suggested shape: sweep lib/VM/JSLib/WebAssembly/WebAssembly.cpp for raw GC pointers and for
references bound into cells, both held across calls that can allocate, concentrating on the
instantiate and link paths; and add explicit -gc-sanitize-handles=1 coverage for whatever the
sweep touches.

    Update: two more instances of the same pattern were found after this issue was filed, in the
    promise helpers rather than the constructors, and were fixed in e72b94ecf on branch wasm-new.
    That makes SEVEN fixed instances, found in three waves -- one, then four, then two -- each wave
    found by looking one step further out than the last, which is not a convergence argument.

      - callPromiseResolve and callPromiseReject each took their payload by value as an unrooted
        HermesValue, performed two JSObject::getNamed_RJS lookups on replaceable globals
        (globalThis.Promise, then Promise.resolve / Promise.reject, so both lookups can run user
        script), and then passed that same unrooted value to Callable::executeCall1. Seven call
        sites across WebAssembly.compile and WebAssembly.instantiate, all passing a value that can
        carry a GC pointer. The reject path clears the runtime's exception root before calling.

    A bounded text scan of the file was then run as triage: intersect the functions that hold a raw
    GC pointer, a raw HermesValue parameter, or a reference obtained from a cell, with the
    functions that call something allocating. 19 functions intersect. 7 were hazards and are now
    fixed; 12 are SAFE; 0 UNCLEAR. The scan is one text pass over one file for one bug class, so a
    clean result is triage, not proof.

    TWO SAFE VERDICTS THAT ARE SAFE FOR A FRAGILE REASON, and are the most useful thing the scan
    produced:

      wasmModuleExports and wasmModuleImports each hold `const auto &` into WasmModuleData across a
      JSObject::putNamed_RJS, which walks the prototype chain and can run a user setter. They are
      safe ONLY because WasmModuleData sits behind a unique_ptr and therefore does not move when
      the JSWebAssemblyModule cell moves. This is structurally identical to the fixed
      wasmExceptionConstructor defect, which held a reference into JSWebAssemblyTag::parameters_ --
      a std::vector stored INLINE in the cell -- with the opposite storage decision producing the
      opposite outcome. If anyone ever inlines WasmModuleData into JSWebAssemblyModule, both
      functions silently become use-after-frees. Nothing near either function records this
      dependency; a comment at the unique_ptr member and at both use sites would be worth adding.

      instantiateModuleImpl depends on the same property for its `moduleData` local.

    STOPPING CRITERION STILL OPEN. Seven found in three waves by successively widening a manual
    search does not tell us the file is clean. What would justify calling this bug class done for
    this file is an open question on this issue, not something the scan answered. Note also that
    cmake-build-sanhandles samples at 1% by default, so any test-based evidence needs
    -gc-sanitize-handles=1 passed explicitly or it is a 1% sample of the paths it runs.
