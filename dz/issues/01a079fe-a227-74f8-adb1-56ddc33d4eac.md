Found 2026-09-07 by external review of `01a079c6-fdd6`, then measured.

Re-exporting an imported global publishes the object that was imported when
the global is MUTABLE, and a freshly constructed one when it is IMMUTABLE.
Node preserves the object in both cases, and so does Hermes for memories and
funcref tables -- so this is Hermes disagreeing with itself as much as with
the spec.

## Reproducer

```wat
(module (import "e" "g" (global i32)) (export "g" (global 0)))
```

```js
// 0,97,115,109,1,0,0,0,2,8,1,1,101,1,103,3,127,0,7,5,1,1,103,3,0
var host = new WebAssembly.Global({value:'i32'}, 42);
var e = new WebAssembly.Instance(new WebAssembly.Module(bytes), {e:{g:host}}).exports;
print(e.g === host, e.g.value);
```

```
                                        Hermes    Node v24.13.1
imported IMMUTABLE global, re-exported:  false        true
imported MUTABLE   global, re-exported:  true         true
```

The value is right either way (`42`); only the identity is wrong.

## Why the spec requires the object

"Create a global object" opens with "Let map be the surrounding agent's
associated Global object cache. If map[globaladdr] exists, return
map[globaladdr]", and "initialize a global object" ends with "Set
map[globaladdr] to global". The constructor registers the host's object under
that address, so re-exporting the same address must return it. Nothing in the
rule mentions mutability. (Cache is per-AGENT, not per-store.)

## Mechanism

`finalizeModule()`'s global export loop bypasses construction only for a
mutable import (`WasmIRGen.cpp:2083-2089`, gated on `importedMutableGlobals_`);
an immutable import falls through to the generic path and gets a new object
built from its value.

Hermes already does the right thing for the neighbouring kinds: an imported
memory keeps `importVal` (`WasmIRGen.cpp:1368`) and is republished at 2183, and
an imported funcref table keeps it at 1247 and is republished at 2234.

## The fix is NOT "publish the imported object for every imported global"

An IMMUTABLE global import may legitimately be satisfied by a raw Number or
BigInt rather than a `WebAssembly.Global` -- `rawAllowed = !mutable_`
(`WasmIRGen.cpp:1020`), accepted at 1041 -- and a raw value has no object to
publish. So:

- when a genuine `WebAssembly.Global` satisfied the import, retain THAT
  object and republish it, keeping the retained object separate from the
  coerced value the constant expressions consume;
- when a raw value satisfied it, construct the exported Global internally
  from the resolved value.

Do not re-read the import property to decide: that is a TOCTOU the link path
already avoids deliberately.
