Recorded as **H19** in the Wasm branch review (`wasm-old-rebased`). Pre-existing;
found 2026-08-25 while reviewing the §4.4 internal-slots pass, not caused by it.

`compileWasmModule` (`lib/WasmFrontend/WasmCompile.cpp:43-48`) runs
`wabt::ReadBinary` and stops. The tree's only `ValidateModule` call is at `:174`,
on the `new WebAssembly.Module(bytes)` path. So `hermesc --wasm` accepts modules
the engine itself rejects, and compiles them to bytecode that reaches unchecked
assumptions at runtime.

A module doing `call_indirect` on an **externref** table — which the Wasm
validator rejects — compiles clean:

```
wat2wasm --no-check ci-extern.wat -o ci-extern.wasm
hermesc --wasm -emit-binary -out ci-extern.hbc ci-extern.wasm     # accepted, exit 0
hermes ... driver.js -- ci-extern.hbc                             # Array replaced
  hermes: HermesValue.h:383: Assertion `isDouble()' failed.       # Aborted
```

The abort is the hot-path type read (`HermesBuiltin.cpp`, `truncateToInt32(
typeVal.unboxToHV(runtime).getNumber())`) pulling an object out of a
script-supplied types array. With a *number* seeded there instead and the
interned type id guessed, a plain JS function in the funcs array was **called
through `call_indirect` with the internal calling convention**.

## Severity — do not overstate this

Reaching it requires the embedder to compile an *invalid* `.wasm` with `hermesc`
and ship the result as trusted bytecode. `.hbc` is trusted by design on this
branch, so this is **not** a hostile-script hole. It is a toolchain-correctness
bug: feed `hermesc` a bad module and you get no diagnostic and undefined
behaviour at runtime, where the JS entry point would have raised a CompileError.

## Fix

Presumably call `ValidateModule` on the `hermesc` path too. Deliberately not done
as part of §4.4 — it is a compiler-behaviour change with its own compile-time
cost and possible test churn, and belongs to whoever owns the frontend.

What §4.4 *did* do is stop three comments and one test from asserting this case
is impossible. Do not reintroduce a "the validator rejects that" justification
anywhere: on this path it does not.

    Fixed by "Fix H19: validate Wasm modules on the hermesc compile path too".

    The root cause was two functions in `WasmCompile.cpp` each parsing a `.wasm`
    into Hermes IR, with validation in only one of them. They are now ONE
    implementation: `compileWasmModule` validates, parses and IRGens, and
    `compileWasmToModuleData` calls it and adds only optimization, bytecode
    generation and the export/import descriptors. So the check cannot be skipped
    by construction rather than by someone remembering to call it.

    Also folded in, because they were the same copy-paste:

    - the wabt feature set was written out THREE times (the two readers plus
      `validateWasmBinary`); one `wasmFeatures()` now feeds all of them, so the
      validator and the reader can no longer drift about what is legal.
    - `validateWasmBinary` built a `wabt::Errors` and discarded it to return
      bool. It now fills an error string via `wabt::FormatErrorsToString`, so
      `hermesc` says WHY a module is invalid instead of "Wasm module validation
      failed". A bool-only overload remains for `WebAssembly.validate()`.

    Covered by `test/wasm/compile-invalid-call-indirect-externref.wat`, which
    pins the validator's specific message rather than a bare non-zero exit --
    verified non-vacuous by removing the validate call and reproducing the exact
    pre-fix pass-through.

    ## The standing instruction in this issue is now INVERTED

    This issue said: "Do not reintroduce a 'the validator rejects that'
    justification anywhere: on this path it does not." On both paths it now
    DOES, and two comments that asserted otherwise (`WasmIRGen.cpp`,
    `HermesBuiltin.cpp`) were corrected in the same commit. The replacement rule
    is narrower: the downstream checks are KEPT, because a fact about the caller
    is not a substitute for the value in hand -- `.hbc` is trusted by design, so
    bytecode compiled before this fix still reaches them.

    ## Consequence worth knowing

    wabt's validator intercepts an out-of-range export index earlier than
    `WasmIRGen::validateExportIndices()` does, so that function is now
    unreachable through either compile entry point (confirmed: the only callers
    are `CompilerDriver` and the unit tests, both `HERMES_ENABLE_WASM`-guarded,
    and the unit test's reader never attaches a `WasmIRGen`). It is deliberately
    kept as defense in depth, and `test/wasm/compile-export-index-oob.wat` now
    pins wabt's message instead. Do not delete it as dead code.

    ## What this did NOT fix

    The two defects this issue's prose described as its own failure modes are
    separate and survive:

    - H17 (`01a0460c-8ed8`) -- the unchecked types-array read.
    - The unchecked funcs-array read, now filed separately.

    Both are now much harder to reach, since neither compile path will accept
    the invalid module they need, but `.hbc` is trusted by design and pre-existing
    bytecode still reaches them.
