Recorded as **H19** in the Wasm branch review (`wasm-old-rebased`). Pre-existing;
found 2026-08-25 while reviewing the §4.4 internal-slots pass, not caused by it.

`compileWasmModule` (`lib/WasmFrontend/WasmCompile.cpp:43-48`) runs
`wabt::ReadBinary` and stops. The tree's only `ValidateModule` call is at `:174`,
on the `new WebAssembly.Module(bytes)` path. So `hermesc --wasm` accepts modules
the engine itself rejects, and compiles them to bytecode that reaches unchecked
assumptions at runtime.

A module doing `call_indirect` on an **externref** table — which the Wasm
validator rejects — compiles clean:

```
wat2wasm --no-check ci-extern.wat -o ci-extern.wasm
hermesc --wasm -emit-binary -out ci-extern.hbc ci-extern.wasm     # accepted, exit 0
hermes ... driver.js -- ci-extern.hbc                             # Array replaced
  hermes: HermesValue.h:383: Assertion `isDouble()' failed.       # Aborted
```

The abort is the hot-path type read (`HermesBuiltin.cpp`, `truncateToInt32(
typeVal.unboxToHV(runtime).getNumber())`) pulling an object out of a
script-supplied types array. With a *number* seeded there instead and the
interned type id guessed, a plain JS function in the funcs array was **called
through `call_indirect` with the internal calling convention**.

## Severity — do not overstate this

Reaching it requires the embedder to compile an *invalid* `.wasm` with `hermesc`
and ship the result as trusted bytecode. `.hbc` is trusted by design on this
branch, so this is **not** a hostile-script hole. It is a toolchain-correctness
bug: feed `hermesc` a bad module and you get no diagnostic and undefined
behaviour at runtime, where the JS entry point would have raised a CompileError.

## Fix

Presumably call `ValidateModule` on the `hermesc` path too. Deliberately not done
as part of §4.4 — it is a compiler-behaviour change with its own compile-time
cost and possible test churn, and belongs to whoever owns the frontend.

What §4.4 *did* do is stop three comments and one test from asserting this case
is impossible. Do not reintroduce a "the validator rejects that" justification
anywhere: on this path it does not.
