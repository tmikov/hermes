Found 2026-09-08 by external review while specifying reference-result
transport. **Identified by code inspection; a repro is the first thing this
issue needs.** Independent of reference types -- it is a defect in the
existing numeric multi-value path.

Numeric multi-value results travel in per-module buffers that are built from
**replaceable globals** and accessed with **ordinary property operations**:

- the buffers come from `globalThis.ArrayBuffer`, `globalThis.Uint32Array`
  and `globalThis.Float64Array` (`WasmIRGen.cpp:1458`)
- result stores and loads are ordinary indexed property accesses
  (`WasmIRGen.cpp:223`, `:313`)

So script can replace those constructors and supply storage whose indexed
getter or setter runs arbitrary JS. Two consequences:

**Substitution.** A replaced accessor can return a different number than the
one the callee stored, so a caller reads a value the callee never produced.

**Reentrancy against shared storage.** The buffers are per-module and reused
across calls. A setter that re-enters an export runs a second multi-value
call, which overwrites the buffer while the outer call's results are still
outstanding. The outer caller then reads a mixture of two activations. The
publication loops interleave stores and loads in signature order, so this
does not need an exotic signature -- `(result i32 i32)` suffices.

The import trampoline's two-pass scheme captures every result before writing
any buffer, which protects the conversion step, but the second pass is still
an ordinary write through replaceable storage (`WasmIRGen.cpp:2804`).

## Why this is filed separately

The reference-types work (`01a074ce-ac97`) gives reference results private,
per-activation storage, which protects **reference** identity. It does not
protect numeric results, and it would be dishonest for that spec to claim a
publication invariant covering "every result" while the numeric half remains
interceptable. So the reference work narrows its invariant to reference
results and points here.

## Fix direction

Allocate the return buffers intrinsically rather than through
`globalThis.*`, and access them through native builtins rather than ordinary
property operations -- the same treatment the reference container gets. That
closes substitution. Reentrancy additionally needs either per-activation
buffers or a guarantee that no script runs between the first committed result
and the caller capturing all of them.

## Related

- `01a0820d-5190` -- the other numeric return-buffer defect: a function reads
  nested-call results from its incoming buffer while passing a module-local
  one. Different bug, same buffers; likely fixed by the same rework.
- `01a074ce-ac97` -- reference types, which specifies the contract this path
  should eventually adopt.

    PROPOSED FIX, with the design space worked out and each claim verified in the tree.

    FIRST, THE FRAMING. Nothing in the Wasm spec or the JS API spec says anything about Float64Array
    in connection with multi-value results. This is purely a Hermes implementation strategy: Hermes
    compiles Wasm to Hermes bytecode, so it needs somewhere to put results 2..N, and it reached for JS
    typed arrays as scratch. A native engine would use a stack slot or a register and the question
    would not arise. So this is not "the spec permits an override to be observable" -- it is an engine
    exposing its own internal scratch space to the program it is running. There is no compatibility
    argument for keeping the current behaviour.

    VERIFIED: THE BUFFERS ARE UNREACHABLE FROM SCRIPT TODAY. Every read of retBufIVar_/retBufFVar_ is a
    createLoadFrameInst feeding internal IR -- call arguments to internal Wasm functions and
    trampolines, and indexed property operations in generated code. A JS import never receives them:
    createImportTrampoline pushes rbI/rbF/refBuf into the INTERNAL call's argument list and builds the
    JS argument list from Wasm params only. No test observes them outside golden-IR CHECK lines. They
    live in the instantiate closure's scope, which e2e-no-closure-escape.wat exists to prove nothing
    escapes from, across 22 enumerated routes.

      Consequence: changing HOW the buffers are allocated is behaviourally invisible. There is no
      identity anyone can observe, no prototype anyone can read, nothing to hold. An earlier draft of
      this note worried about "changing identity"; that was wrong, and it is recorded here because a
      spurious caveat on a safe change is an argument for not making it.

    THREE OPTIONS. They form a ladder and the middle one is dominated.

      A. READ PRISTINE CONSTRUCTORS FROM HermesInternal. Stash ArrayBuffer / Uint32Array /
         Float64Array as named properties on HermesInternal and have WasmIRGen read those instead of
         globalThis.

         This works, and the lockdown is real rather than conventional -- all verified:
           - globalThis.HermesInternal is defined with constantDPF: non-writable, non-configurable
             (GlobalObject.cpp, the define site).
           - The HermesInternal object itself is preventExtensions'd (HermesInternal.cpp).
           - Its own properties are defined with constantDPF too: writable=0, configurable=0.
           - It is ALWAYS installed. flags.enableHermesInternal only gates the extra methods added
             after an early return, and the code there says so: "All functions are known to be safe
             can be defined above this flag check." A property defined ABOVE that check is
             unconditional.
         So for read purposes the lookup target is as immune to script as a builtin-table index.
         Cost: two property loads instead of one, at instantiation only -- the buffer is built once
         per instance. Nil.
         NO NEW BUILTIN, which is the attraction.
         THE TRADEOFF: it is a script-visible capability. HermesInternal.Float64Array lets any script
         recover the pristine constructor after another script overrode globalThis.Float64Array, which
         is not recoverable today. Whether that matters depends on whether any embedder sandboxes by
         overriding globals. That is a product decision, not a technical one.

      B. AN INTERNAL PROPERTY instead of a named one -- invisible to script, using the mechanism the
         funcref brand already uses (Predefined::InternalPropertyWasmFuncClosure).

         DOMINATED, and here is why, checked rather than assumed. Internal properties live in a
         SEPARATE SYMBOL SPACE: Predefined::IProp, generated from InternalProperties.def, enumerated
         before Str in the same numbering. IRBuilder's createLoadPropertyInst takes either a Value*
         (a literal string) or an Identifier -- both ordinary string symbols. A reserved IProp symbol
         is not string-addressable, and there are ZERO occurrences of "InternalProperty" anywhere in
         lib/IRGen/, lib/WasmIRGen/ or lib/BCGen/. They are read exclusively from native code, via
         getNamedSlotValueUnsafe with a descriptor -- which is exactly why the funcref brand goes
         through the wasmSetFuncInfo / readWasmFuncInfo builtins rather than a direct load.
         So generated IR cannot name one, and B needs a builtin to perform the read. That defeats its
         own purpose, and once a builtin is in play option C is strictly better: it removes the
         property read entirely rather than routing it through native code.

      C. A BUILTIN THAT ALLOCATES THE VIEWS INTRINSICALLY, the way Task 10 already did twice.

         JSTypedArray<double, CellKind::Float64ArrayKind>::allocate(runtime, length) (JSTypedArray.h)
         allocates without consulting globalThis at all; TypedArray.cpp already uses exactly that
         shape for Uint8Array, and allocateToSameBuffer covers the two-views-on-one-buffer
         arrangement. This is the same move as wasmMakeResultArray (which replaced a globalThis.Array
         call to close defect (c) of the reference work) and wasmAllocRefBuf. No property read at all,
         nothing script-visible, one new builtin -- five registration edit sites, per the recipe on
         01a08442-8682.

      SO THE REAL CHOICE IS A vs C: no-new-builtin versus no-capability-leak. B is a trap that looks
      like the best of both and is neither.

    WHAT ANY OF THEM CLOSES, and what none of them does:

      CLOSED OUTRIGHT: this issue. No replaceable constructor, no accessor on the reads.

      THE UNSOUNDNESS IN 01a0850f-ac3e GOES AWAY, because a pristine Float64Array can only yield
      numbers, so wasmValTypeToIRType(F64) = Type::createNumber() stops being a lie and asNumber's
      isNumberType() short-circuit stops being reachable with a non-number. (The full chain: an
      uncoerced buffer read is pushed with no AsNumberInst, passed as an argument to an internal call,
      annotated `number` on the callee's parameter, asNumber returns it unchanged, FAdd lowers to
      AddN, and the interpreter does getNumber() -> getDouble() on both operands and encodes the
      result as a TRUSTED number.)

      NOT CLOSED -- the f32 ROUNDING gap. Nothing on this path rounds an f64-typed slot to f32
      precision. That is wrong regardless of who owns the buffer, and it is the half of 01a0850f-ac3e
      that survives any of A, B or C. It needs its own fix on the f32 arm.

      NOT CLOSED -- 01a0820d-5190. A nested call reading a different buffer than the one it passed
      survives private, non-interceptable storage, because its cause is passing one buffer and reading
      another. Retracted once already on that issue; retracted again here so nobody bundles it.

    NOTE ON SCOPE: all THREE constructors need whichever treatment is chosen, not just Float64Array. A
    replaced ArrayBuffer poisons both views.
