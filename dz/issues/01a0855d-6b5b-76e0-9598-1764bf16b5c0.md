WasmIRGen emits a generic guard before per-kind import validation (lib/WasmIRGen/WasmIRGen.cpp,
"Check import value is not undefined"): if the loaded property is undefined, it raises
LinkError: module has no import <mod>.<field>.

Node v24.13.1 has no such concept for global imports. It reads the property -- undefined if
absent -- and applies the type rule, so present-and-undefined and absent are indistinguishable
and the diagnostic is a TYPE error, not a missing-import error.

Measured, node v24.13.1, module `(import "e" "b" (global externref))`:

  {e: {b: undefined}}   linked, get() -> undefined
  {e: {}}               linked, get() -> undefined
  {e: {b: null}}        linked, get() -> null
  {e: {b: {}}}          linked, get() -> the object

and for `(import "e" "f" (global funcref))` plus `(import "e" "n" (global i32))`:

  f absent      LinkError: ... Import #0 "e" "f": function-typed object must be null
                (if nullable) or a Wasm function object
  f undefined   same message
  n absent      LinkError: ... Import #1 "e" "n": global import must be a number, valid Wasm
                reference, or WebAssembly.Global object
  n undefined   same message

So Hermes diverges in two ways:

  1. EXTERNREF: Hermes refuses what node accepts. Being fixed with the reference-types work --
     an immutable externref global import is exempted from the guard, because undefined is a
     legal externref value and node links it.

  2. FUNCREF AND NUMERIC: Hermes refuses, correctly, but with the WRONG MESSAGE. It says the
     import is missing when the import may well be present and merely of the wrong type. Node
     reports a type error naming what was expected. NOT fixed: changing those messages touches
     four existing pinned tests, and it is a diagnostic-quality question rather than a
     correctness one.

Only global imports were measured. The guard is generic across all import kinds -- function,
table, memory, global -- so whoever fixes the messages should measure the other three against
node rather than assuming they match.

    One more measurement in the same area, found while reviewing the Task 5 exemption.

    A NON-OBJECT import namespace now links silently for an immutable externref import. `{e: 5}` and `{e: 'x'}` instantiate and hand the module `undefined`, because the property read off a primitive yields `undefined` and that is a legal externref value which no longer takes the missing-import guard. Before the exemption the guard caught these by accident.

    Node throws a TypeError for a non-object namespace. Hermes never checks the namespace's type at all -- it only checks that the namespace itself is not `undefined` -- so this is a corner of an already-missing check that the exemption newly exposes, not a regression the exemption introduced. `{e: null}` gives a raw `TypeError: Cannot read property 'b' of null` from the property read, which is pre-existing and unrelated to the exemption.

    Deliberately not fixed in Task 5: the fix is a namespace type check, which belongs with the message work filed here rather than with the link path.
