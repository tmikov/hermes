Found 2026-09-06 while explaining the global-export path for
`01a074ce-ac97`. Not that bug: no reference types are involved, nothing
crashes, and the two fixes are independent. Plain `(mut i32)` reproduces it.

A global that the module DEFINES, declares mutable, and EXPORTS is handed to
JavaScript as a **copy** taken at instantiation time. The module keeps
reading and writing its frame slot; JS reads and writes `value_` inside the
`JSWebAssemblyGlobal` cell. Nothing joins them. Both sides accept every
write and neither is told, so the two diverge silently.

The JS API has no such copy anywhere: `CreateGlobalObject(store, globaladdr)`
stores a global ADDRESS, and `Global.prototype.value` is defined as
`global_read` / `global_write` against the store at that address -- the same
address the instance's own `global.get`/`global.set` use. One cell, by
construction.

## Reproducer

```wat
(module
  (global $g (export "g") (mut i32) (i32.const 0))
  (global    (export "c")      i32  (i32.const 7))
  (func (export "inc") (global.get $g) (i32.const 1) (i32.add) (global.set $g))
  (func (export "get") (result i32) (global.get $g)))
```

```js
var e = new WebAssembly.Instance(new WebAssembly.Module(bytes)).exports;
print(e.g.value, e.get());   // 0 0
e.inc();
print(e.g.value, e.get());   // Node: 1 1     Hermes: 0 1
e.g.value = 100;
print(e.g.value, e.get());   // Node: 100 100 Hermes: 100 1
e.inc();
print(e.g.value, e.get());   // Node: 101 101 Hermes: 100 2
```

Measured with `cmake-build-asan/bin/hermes` against `node v24.13.1`. Broken
in both directions: the module's writes never reach JS, and JS's writes
never reach the module. No error either way.

The value COERCION is correct and matches Node exactly -- `3.7` -> `3`,
`2**32+5` -> `5`, a `valueOf` object -> its number, and writing an immutable
global raises a TypeError. Only the storage is wrong.

## Mechanism

`finalizeModule()`'s global-export loop reads the frame slot ONCE and passes
that value to the constructor (`WasmIRGen.cpp:2043-2158`: the constructor
lookup at 2064-2069, the imported-mutable bypass at 2083, the single frame
read at 2091, construction at 2154, publication at 2157). Optimized IR for
the module above:

```
       StoreFrameInst %0, 0, [%VS0.global_0]        ; module storage, initialized
  %26 = LoadPropertyInst %25, "Global"
  %27 = LoadFrameInst [%VS0.global_0]               ; read ONCE
  %28 = AllocObjectLiteralInst
        StorePropertyStrictInst "i32", %28, "value"
        StorePropertyStrictInst true,  %28, "mutable"
  %33 = GetConstructedObjectInst ...                ; new WebAssembly.Global(desc, %27)
        StorePropertyStrictInst %33, %22, "g"
```

`wasmGlobalValueSetter` (`WebAssembly.cpp:2288-2329`) then writes `value_`
in that cell and returns. It touches no `Environment`, and holds no
reference to one -- the module's storage is a `Variable` in a closure scope
the runtime cannot reach. Because the descriptor carries `mutable: true`,
the setter's mutability check passes and the write is accepted, then lost.

This is stated in the code, three lines above the loop
(`WasmIRGen.cpp:2050-2051`):

> // The value is a snapshot at init time; mutable globals won't reflect
> // later mutations (that would require live wiring, a separate change).

It had not been filed, which is why this issue exists.

## What is NOT affected

The table below is about **value coherence** only -- whether the two sides
can disagree about the value. It is not a claim that everything else on
those rows is correct; two of them have separate defects, noted underneath.

| configuration | where the value lives | value coherence |
|---|---|---|
| imported mutable global (and re-export of one) | the host's `WebAssembly.Global` | correct, verified identical to Node |
| imported immutable global | frame slot (resolved at link) | correct (but see identity, below) |
| exported immutable global | frame slot; the copy cannot go stale | correct (but see extended constants, below) |
| **exported mutable global the module defines** | **frame slot AND the cell** | **broken** |

An imported mutable global is correct because `global.get`/`global.set`
route through the `wasmGlobalGet`/`wasmGlobalSet` builtins against the host
object, and its frame slot holds only a link-time snapshot that Wasm
validation makes unreadable -- a constant expression may not read a mutable
global. Verified: Node rejects a data-segment offset reading a mutable
imported global with "mutable globals cannot be used in constant
expressions" and accepts the immutable form.

### Separate defects on those rows, found by external review

None of these is this bug and none expands this fix, but the rows above must
not be read as blanket "correct".

**Identity of a re-exported immutable import is not preserved.** Measured:

```
                                        Hermes    Node v24.13.1
imported IMMUTABLE global, re-exported:  false        true      <- exports.g === host
imported MUTABLE   global, re-exported:  true         true
```

The mutable bypass at `WasmIRGen.cpp:2083-2089` publishes the imported
object; an immutable import falls through and gets a fresh `Global` built
from its value. Hermes is inconsistent with itself here, not only with Node.
The JS API creates an exported Global from a *global address*, and "create a
global object" begins by consulting a per-agent cache keyed on that address
-- "Let map be the surrounding agent's associated Global object cache. If
map[globaladdr] exists, return map[globaladdr]" -- while "initialize a global
object" is what registers it. Nothing in that rule is conditioned on
mutability. Note the fix is not simply "publish the imported object for
every imported global": an immutable import may legitimately be satisfied by
a raw Number or BigInt (`rawAllowed = !mutable_`, `WasmIRGen.cpp:1020,1041`),
which has no object to publish, so the object has to be retained when a
genuine Global satisfied the import and constructed internally from the
resolved value otherwise. Filed as `01a079fe-a227`.

**An i64 global with an extended constant initializer gets the wrong value.**
Measured, all valid modules:

```
                                        Hermes    Node
(i32.add (i32.const 1) (i32.const 2))      3        3     <- i32 is correct
(i64.add (i64.const 1) (i64.const 2))      2        3
(i64.mul (i64.const 3) (i64.const 5))      5       15
```

It takes the LAST constant parsed. i64 constants and i64 arithmetic are not
recorded in `initExpr` at all -- only the i32 forms are
(`BinaryReaderHermesIRGen.cpp:584-598`; `global.get` is recorded regardless
of type at 693-701) -- so an i64 extended constant falls back to the scalar
`initKind`/`initValue` pair, and `initializeGlobals` stores that
(`WasmIRGen.cpp:7654`). Silent, like this bug. Filed as `01a079fe-eff6`.

**Two export names for one global yield two objects.** Same "create a global
object" cache rule as above, so the second export of a global address must
return the first object. Measured:

```
                                        Hermes    Node v24.13.1
one global,  two export names, same object:  false    false
one memory,  two export names, same object:  true     true
```

Both engines are non-conforming here for globals, and both conform for
memories. Recorded because the fix constructs one Global per export ENTRY
(`WasmIRGen.cpp:2154`); construct and cache one per global INDEX instead and
the divergence goes away for free. Deferring it is fine -- it is a
spec/implementation discrepancy, not a value-coherence bug -- but the
storage-coherence test in the acceptance criteria is not optional. Filed as
`01a079ff-5dc0`.

## How often it occurs

Scanned every `.wasm` reachable locally -- Node's test corpus plus this
repo's examples and fixtures, 74 modules:

```
with a mutable global they DEFINE            : 34
with a mutable global they IMPORT            :  2
that EXPORT a mutable global they define     :  2   <- the broken case
```

Defining a mutable global is routine; exporting one is rare. The two that do
are Node's `globals.wasm` and `dep.wasm` -- the fixtures written to test this
very feature, and the same two that crash the compiler under
`01a074ce-ac97`. So: a path most compiled output does not take, that every
conformance test for the feature takes immediately.

Do not confuse this with Node's `test-wasm-globals-all-types.mjs`, which
asserts that `wasmExports.localMutI32` stays at its old value after a
mutation. That is the ESM integration exposing globals as unwrapped values
in the module namespace, where live bindings are not implemented yet (the
test says so in a comment). The JS API path measured above is live in Node.

## Fix direction

Preferred (tmikov): make the exported `WebAssembly.Global` **closure-backed**.
At instantiation the compiler creates a getter closure and, for a mutable
global, a setter closure over the module's top-level scope, and hands them to
the Global. `.value` then calls them, so the frame slot stays the single
source of truth and the module's own `global.get`/`global.set` remain plain
`LoadFrameInst`/`StoreFrameInst` -- no cost inside the module at all.

The alternative -- route the module's accesses through
`wasmGlobalGet`/`wasmGlobalSet` the way an imported mutable global already
does -- reuses working machinery but taxes every access with a builtin call
plus a re-narrowing coercion, and a BigInt build/split per access for i64.

Notes for whoever implements the closure form:

- **Every** newly constructed global export -- live mutable and immutable
  snapshot alike -- must be built internally by the engine, never by calling
  a JS-reachable constructor. This is a requirement, not one of two options:
  see the interposition comment below for why a post-hoc brand check cannot
  substitute for it.
- The cell needs GC-visible closure fields (`GCPointer<Callable>`) plus
  `mb.addField`. `JSGeneratorObject` is the closer example than
  `JSWebAssemblyTable`, whose `elements_` is a `GCPointer<JSArray>`. Mind
  initialization in the constructor, barriered writes, rooting across any
  call, and that the cell's size and overlap-slot metadata already depend on
  its C++ layout. Keep `valType_` and `mutable_` where they are: the brand
  check, the immutable TypeError and `wasmLinkGlobal`'s matching all read
  them.
- Only mutable exported globals are closure-backed. An immutable one is
  value-correct as a snapshot and should stay one, which keeps the two
  representations aligned with the two ways the value is consumed (see the
  `wasmLinkGlobal` point).
- `wasmLinkGlobal` does NOT need to call a closure. For a MUTABLE import the
  object is kept and the returned value is discarded -- `globalObjValue` at
  `WasmIRGen.cpp:1068` selects the object, and the frame slot it would feed
  is the unreadable snapshot. Only an immutable import consumes the value,
  and an immutable global is never closure-backed. No new sentinel is
  needed: for a live global, return the matched `Global` OBJECT as the
  success answer, after the type and mutability match at
  `HermesBuiltin.cpp:2389` and before any backing value field is read.
- `wasmGlobalGet`/`wasmGlobalSet` DO need to call the closures, for the
  cross-module chain where module B imports module A's exported mutable
  global. Be accurate about what that costs: both builtins ALREADY throw on
  invalid arguments, and `wasmGlobalGet` already allocates a BigInt for an
  i64 global. What closure invocation adds is interpreted execution and its
  rooting and reentrancy obligations -- not the first possibility of
  allocation or of an exception.
- `initializeGlobals()` currently calls `wasmGlobalGet` for every mutable
  import (`WasmIRGen.cpp:7577`). Left alone, that would invoke the EXPORTING
  module's getter during the IMPORTING module's instantiation, even when no
  Wasm code reads the global. Resolve it by skipping the entire per-import
  snapshot initialization for a mutable import -- an early `continue`, not
  just deleting the `emitGlobalGet` call, which would leave the Global object
  flowing into `coerceImportedGlobalValue` and then into `emitBigIntToI64`,
  which rejects it. Keep the slot allocation and the `globalSlotIndex_`
  mapping: later defined globals and i64 pairs depend on it. The snapshot is
  dead for VALID modules only -- wabt refuses a mutable `global.get`
  throughout constant-expression context -- and `hermesc --wasm` does not
  validate (`01a0460b-1ea9`), so an invalid AOT input can still reach those
  constant-expression reads.
- Specify the setter closure ABI, or the coercion moves and becomes
  observable. The native setter performs `ToNumber` exactly once (or the
  BigInt check for i64), refuses an immutable global before any closure is
  consulted, re-derives its raw `JSWebAssemblyGlobal` pointer after the
  conversion safepoint, and passes an already-numeric value (or a BigInt for
  i64) to the closure. The closure does the narrowing: `AsInt32Inst` for
  i32, `emitFround` for f32 -- the instructions `coerceImportedGlobalValue`
  (`WasmIRGen.cpp:7736`) uses. NOT "the same as the module's own
  `global.set`", which narrows nothing and stores an already-typed value
  (`WasmIRGen.cpp:7884`). If conversion throws, the outer setter does not
  commit its assignment -- but a `valueOf` that mutated the global before
  throwing keeps its mutation; that is required, not a bug to undo.
- i64 needs the closures to assemble and split the lo/hi pair.
  `emitI64ToBigInt` / `emitBigIntToI64` already exist. `retBufIVar_` is
  ALWAYS allocated, with an 8-byte minimum (`WasmIRGen.cpp:649`), so
  availability is not the question; the open question is the documented
  reentrancy invariant at `WasmIRGen.cpp:1446` -- nothing that can re-enter
  Wasm or run arbitrary JS may write the buffer between a producer and its
  consumer.
- An exported live Global strongly retains its captured `Environment`, and
  can thereby retain other globals, the memory, the tables, imports and
  closures -- whatever the optimizer leaves reachable in that graph. Today a
  snapshot Global retains no module environment through its numeric backing
  value (it is still an ordinary `JSObject` with the usual references).
  Believed correct (the spec's Global holds a store address, with the same
  implication) but decide it deliberately.
- Adding a builtin for the internal construction has a disabled-build
  consequence that is easy to miss: when `HERMES_ENABLE_WASM` is off, the
  wasm builtin ids are registered by one loop over the contiguous range
  `HermesBuiltin_wasmTrap .. HermesBuiltin_wasmSetFuncInfo`
  (`HermesBuiltin.cpp:3888-3900`). A builtin appended after `wasmSetFuncInfo`
  falls outside that range and resolves to nothing, so the upper bound must
  move with it. Inserting before the `JS_BUILTIN` block also shifts
  `_firstJS` and needs a `BYTECODE_VERSION` bump (`01a0460c-4361`).
- Second-order benefit, relevant to `01a074ce-ac97`, stated narrowly: for a
  MUTABLE global that a module defines and exports, the value lives in the
  frame slot, so that one case needs no reference-capable value slot in the
  cell. Reference-capable storage is still required for immutable exports
  and for globals built by the public constructor, so this does not remove
  the cell-layout work for reference types in general.

Acceptance criteria: keep only the exported Global alive across a GC and
read it back; i32/i64/f32/f64 writes visible in both directions; A->B->C
import and re-export chains; start-function mutations visible to JS; a
`valueOf` callback that reads and mutates the same live global; and STORAGE
coherence across multiple export names -- a write through either name, or
from Wasm, must be visible through both. That last one is required here
because the loop constructs one Global per export entry; it is about the
value, and is independent of the `===` identity discrepancy above, which is
deferred. The identity assertions themselves belong to the separately filed
issues, not to this fix.

Fix this one first: it is silent, it needs no exotic types, and the
reference-type work depends on the storage decision made here.

    ## Corrections to the interposition comment, after external review

    Two claims in the comment above are wrong. The body's "Fix direction" now
    carries the corrected requirement; this records what was wrong.

    **1. "add a brand check on the constructed object" does not work.** A
    replacement constructor can return a GENUINE `WebAssembly.Global` whose type
    and mutability match the declaration and which has nothing to do with this
    module's storage, and can run arbitrary code before returning or throwing. A
    brand check accepts it. `wasmLinkGlobal` checks only brand, type and
    mutability (`HermesBuiltin.cpp:2374`), so it cannot tell the difference
    either. Internal construction is therefore a REQUIREMENT for every NEWLY
    CONSTRUCTED global export, not one of two acceptable routes. It does not
    apply to a re-export that republishes an already-imported object, which
    this engine does not construct at all. The body has been amended.

    **2. "the memory and table export paths DO brand-check" is true of funcref
    tables only.** Measured on a module defining and exporting an `externref`
    table, with `globalThis.WebAssembly.Table` replaced:

    ```
                                     Hermes          Node v24.13.1
    externref table export:          HIJACKED        genuine Table
    funcref   table export:          LinkError       genuine Table
    memory    export:                LinkError       genuine Memory
    ```

    A defined memory and a defined funcref table are brand-checked at
    construction (`WasmIRGen.cpp:5929`, `7049`) and their export loops republish
    the already-checked object. The externref table export path is a separate
    fallback that calls the replaceable constructor and publishes the result
    unchecked (`WasmIRGen.cpp:2250`, `2274`). So the correct statement is:
    defined memory and funcref table exports check; the externref table export
    and the global export do not.

    Ownership, to settle the earlier ambiguity: the GLOBAL export
    interposition is fixed HERE -- the body's "Fix direction" requires
    internal construction, so no separate issue owns it. The EXTERNREF TABLE
    export interposition is a different code path with a different fix and is
    not touched by this work; filed as `01a079ff-5d7b`.

    ## A derived requirement that measurement contradicted, then the spec upheld

    The review argued from the JS API's object cache that two export names for
    the same global must yield the same object. Node does not do that, which
    looked at first like the derivation being wrong:

    ```
    one global, two export names -> same object:  Hermes false   Node false
    one memory, two export names -> same object:  Hermes true    Node true
    ```

    The spec text settles it against both engines. "Create a global object"
    opens with "Let map be the surrounding agent's associated Global object
    cache. If map[globaladdr] exists, return map[globaladdr]", and "initialize
    a global object" ends with "Set map[globaladdr] to global". "Create an
    exports object" reaches a global export through that same algorithm, so the
    second export of one global address must return the first object. The cache
    is per-AGENT, not per-store.

    So Hermes and V8 are both non-conforming for globals here, and both conform
    for memories. It is a spec/implementation discrepancy rather than an
    unsupported derivation -- recorded, deferred, and carried in the body as a
    note rather than as work for this fix. The re-export identity divergence in
    the body is a separate matter and stands on its own evidence.
