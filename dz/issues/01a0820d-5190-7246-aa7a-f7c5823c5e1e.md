Found 2026-09-08 by external review while specifying reference-result
transport. **Identified by code inspection, not yet reproduced at runtime** --
a repro is the first thing this issue needs.

Multi-value results travel in a per-module return buffer, and a function can
end up writing one buffer while reading another.

## The mismatch

- A function that needs a return buffer receives it as PARAMETERS:
  `beginFunction` sets `retBufI_`/`retBufF_` from
  `getJSDynamicParam(1)`/`(2)` (`WasmIRGen.cpp:2900-2910`).
- `onCall` hands a nested callee the **module-local** buffer, loaded from
  `retBufIVar_`/`retBufFVar_` (`WasmIRGen.cpp:4198-4208`).
- `emitRetBufLoads` reads a nested call's results back through the
  **incoming** `retBufI_`/`retBufF_` (`WasmIRGen.cpp:292-300`).

Its comment states the assumption: "There is one buffer per module, so the
top-level view is the object the callee was handed." That holds while every
caller passes the module's own buffer -- true for direct calls within a
module and for the export wrapper, which loads `retBufIVar_`.

`call_indirect` breaks it: it passes the CALLER's buffers to whatever
function the table slot holds (`WasmIRGen.cpp:4277`). So when module B
indirect-calls a function of module A, that function's `retBufI_` is **B's**
buffer. If it then makes a nested multi-value call, `onCall` passes **A's**
module-local buffer to the callee, the callee writes there, and
`emitRetBufLoads` reads B's buffer instead. The results read are whatever B's
buffer last held.

## Shape of a repro

Two modules. A exports a multi-value function that itself performs a nested
multi-value call. B imports that function into a table and reaches it with
`call_indirect`. Compare against the same call made directly.

## Scope

Numeric multi-value results only; single-value returns come back directly and
are unaffected (`WasmIRGen.cpp:4329`). This is independent of reference types
-- it is a defect in the existing numeric path -- but it matters to that work
because "follow the numeric return buffer" is otherwise the obvious
prescription for reference-result transport, and it would copy this bug.

## Fix direction

Make the buffer a caller-supplied argument threaded consistently: a callee's
result stores target the buffer its caller supplied, and a nested call's
result loads target exactly the buffer passed to that nested call. Today the
first is true and the second is not.

## Related

- `01a074ce-ac97` -- reference types. Its design needs the same transport
  contract for reference results and must not inherit this defect.
