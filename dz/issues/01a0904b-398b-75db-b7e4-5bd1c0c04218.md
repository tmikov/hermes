Recorded 2026-09-11, when WasmIRGen stopped reading constructors from
globalThis and started reading pristine ones from HermesInternal.intrinsics.

Several defensive checks exist specifically to cope with backing storage the
engine did not allocate:

- `wasmCheckTableArrays` -- that the three externref-table arrays really are
  arrays.
- The writability check in the table-set funnel, which raises "Wasm table
  storage is not writable" rather than believing a frozen JSArray's silent
  `false`.
- The length rollback in `wasmTableGrow`, which puts all three arrays back
  when one refuses to lengthen. Its absence was previously invisible to the
  whole suite until e2e-table-slot-invariant.wat started printing all three
  lengths.
- The checked casts in the retbuf/memory-view builtins (writeI64ToRetBuf and
  friends), which reject a non-typed-array instead of vmcasting it.

Every one of these was driven from script by replacing globalThis.Array /
Uint8Array / Uint32Array before instantiation. That is no longer possible: a
funcref table's arrays are internal fields of a genuine WebAssembly.Table, and
every other allocation now goes through HermesInternal.intrinsics, which is
non-writable, non-configurable and non-extensible.

So the checks are correct, kept, and unreachable -- which also means untested.
The probes that used to cover them were REMOVED from
e2e-table-slot-invariant.wat and e2e-hostile-typed-array.wat rather than left
green-but-inert, because a test that can no longer construct its own
precondition passes for the wrong reason. e2e-table-copy-alias.wat lost its
partial-aliasing section the same way.

WHAT TO DECIDE, not decided here:
  (a) accept them as defence in depth and leave them untested;
  (b) give tests a way to inject storage -- which means a
      -Xhermes-internal-test-methods hook that swaps the intrinsics holder,
      and that hook is itself a footgun, since the whole value of the holder
      is that nothing can swap it;
  (c) drop the now-unreachable checks, trading code the compiler no longer
      needs against the next caller who reaches these builtins by a route
      nobody has thought of.

    CORRECTION AND DECISION, 2026-09-14. Two of the four items listed above do not
    survive scrutiny, and the reasoning that framed the whole issue was wrong.

    THE FRAMING WAS WRONG. I argued elsewhere that these checks still guard a live
    boundary because a PRIVATE_BUILTIN is reachable from any bytecode emitting a
    CallBuiltin with its index. BYTECODE IS TRUSTED in Hermes's threat model.
    Hand-crafted bytecode is not an attack vector, so that is not a reason to keep
    a check, and a gtest calling a builtin with a forged argument is not a test of
    a reachable state. The comments in this tree that use that phrasing as a
    security argument have been rewritten; two of them already said bytecode was
    trusted, and the rest contradicted them.

    So option (a) is accepting dead code, option (b) is adding a real footgun to
    exercise an unreachable state, and option (c) is the leading one. DECIDED: (c).

    BUT ONLY TWO OF THE FOUR ARE ACTUALLY DEAD.

      DROP -- wasmCheckTableArrays. Its whole job is confirming three values are
      arrays, and they now provably are: an externref table's come from the
      pristine Array, a funcref table's are internal fields of a genuine
      WebAssembly.Table.

      DROP -- the writability check in the table-set funnel. JSObject::setOwnIndexed
      answers false only for sealed or frozen storage, which engine-allocated
      arrays never are. Becomes an assert.

      KEEP -- the length rollback in wasmTableGrow. The description above says it
      "puts all three arrays back when one refuses to lengthen", which is not what
      the code does. It rolls back when setWasmTableSlot throws OUT OF MEMORY
      part-way through filling the new slots, then answers -1 as table.grow's
      "could not allocate". That is reachable from ordinary Wasm under memory
      pressure and has nothing to do with who allocated the storage. The old test
      used a frozen array only as a cheap way to SIMULATE the failure; what was
      lost is the simulation, not the reachability.

      KEEP -- the attached check in wasmTypedArrayArg. The claim that script has no
      way to detach an ArrayBuffer is false, and was measured in one build
      configuration and generalised. lib/VM/SerializedValue.cpp implements
      StructuredSerializeWithTransfer, including serializeArrayBufferForTransfer,
      and Worker.postMessage reaches it with a transfer list. installWorker is
      gated on JSI_UNSTABLE, which is OFF in the CLI used for the probe and ON in
      builds that want Workers. With it on, script can transfer and so detach a
      Wasm memory's buffer, leaving the module's views detached -- which is
      precisely what this check catches. Its dyn_vmcast half is dead, but the two
      share one condition and splitting them buys nothing.

      wasmArrayArg's check IS purely a type check with no attached-equivalent, so
      it goes the same way as wasmCheckTableArrays.

    REMOVED:
      - the wasmCheckTableArrays builtin entirely -- body, call site in
        createTables(), and all four registration points.
      - the writability report in wasmStoreTableElement; it is an assert now, and
        the "Wasm table storage is not writable" diagnostic is gone.
      - wasmArrayArg's checked cast, now a vmcast, with the nine dead null guards
        at its call sites and the raiseWasmLinkError helper it was the last user
        of.

    KEPT, with the reasons on the correction above:
      - the wasmTableGrow rollback, which handles OOM mid-fill and not frozen
        storage;
      - wasmTypedArrayArg's checks, because Worker.postMessage with a transfer
        list reaches serializeArrayBufferForTransfer and so can detach a Wasm
        memory's buffer wherever JSI_UNSTABLE is on.

    Also rewritten: seven comments across HermesBuiltin.cpp and Builtins.def that
    used "a PRIVATE_BUILTIN is reachable from ANY bytecode" as a threat-model
    argument. Bytecode is trusted; that reasoning is void. Two comments in the
    tree already said so and the rest contradicted them, which is how the wrong
    reasoning survived. The checks that remain now say what they are actually for
    -- a compiler bug, or a genuinely arbitrary input such as an import.
