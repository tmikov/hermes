Found 2026-09-14 while testing the `delegate` fix, and verified.

`catch_all` catches a Wasm TRAP. The spec is explicit that it must not:
traps are not exceptions, and no handler in the module sees one.

    (module (func (export "p") (result i32)
      (try (result i32)
        (do (unreachable) (i32.const 0))
        (catch_all (i32.const 1)))))

    p() = 1

It should have trapped out of the function. The cause is that a trap is
raised as an ordinary JS throw, and catch_all is lowered to something
that accepts anything thrown, so nothing tells the two apart.

The consequence is not only that traps are swallowed. It makes tests
that rely on a trap being observable silently useless: the spec suite's
own `delegate-correct-targets`
(`external/wasm-testsuite/tests/legacy/try_delegate.wast:100`) puts
`catch_all unreachable` on every handler a delegation must skip, so that
landing on the wrong one traps. Here a wrong landing traps and the trap
is then caught by the OUTERMOST catch_all, producing the same answer as
a correct landing. The function passed both before and after the
delegate fix. test/wasm/e2e-try-delegate.wat keeps it, because it is the
spec's, and carries `delegate-targets-obs` beside it -- the same shape
with handlers that return numbers instead of trapping -- to do the
discriminating.

A fix needs traps to be distinguishable from Wasm exceptions at the
handler, which probably means a distinct carrier rather than a bare JS
throw. `throw` from JS into Wasm and `WebAssembly.Exception` both have
to keep working, so this is not a matter of narrowing what catch_all
accepts.

    ANALYSIS, 2026-09-18, at 67392ff7c. Everything below is measured, on the
    same modules through both engines, not read off the spec.

    ## What the code does today

    A Wasm `throw $tag` builds a JS ARRAY -- `[tagObject, payload0, ...]` --
    and throws it (`WasmIRGen.cpp:6127` onThrow, via emitCreateException at
    `WasmHelpers.cpp:381`).

    `catch $tag` calls wasmMatchException (`HermesBuiltin.cpp:1089`), which
    returns the array only when the caught value is a JSArray whose element
    0 is that exact tag object, and undefined otherwise, which falls through
    to the next clause. So `catch $tag` refuses a trap already, by
    construction rather than by intent.

    `catch_all` (`WasmIRGen.cpp:6078` onCatchAll) performs NO test. It takes
    whatever CatchInst produced and runs the handler.

    A trap is `runtime.raiseError(...)` (`HermesBuiltin.cpp:276` wasmTrap and
    the arithmetic traps beside it) -- a plain JS Error, indistinguishable
    from any other.

    So nothing in a thrown value says "trap rather than exception", and
    catch_all would not look if it did.

    ## Measured against node v24.13.1

    Four shapes, one module each, run through both:

    | shape                          | node                | hermes        |
    |--------------------------------|---------------------|---------------|
    | catch_all around `unreachable` | escapes RuntimeError| RETURNS 1     |
    | catch_all around a JS import
      that throws `new Error`        | returns 1           | returns 1     |
    | catch $t around `unreachable`  | escapes RuntimeError| escapes Error |
    | catch $t around the JS import  | escapes Error       | escapes Error |

    Exactly ONE behavioural divergence: catch_all swallows a trap. The other
    three agree, and the only remaining difference in them is the type name
    on the trap, which is 01a074ce-ff7d.

    Note what the second row settles: catching a foreign JS exception is
    CORRECT. Whatever test catch_all grows must let those through to the
    handler, so "only accept the [tag, ...] array" would be wrong.

    ## The check cannot be `instanceof WebAssembly.RuntimeError`

    Thrown from an import, node CATCHES a RuntimeError that script
    constructed:

        e: { f() { throw new WebAssembly.RuntimeError('forged by script'); } }
        jsThrow(RuntimeError): returned 1

    while a real trap in the same module escapes. So V8 does not identify
    traps by class -- it marks them internally -- and a class test here would
    both diverge from node and hand script a way to make a handler ignore an
    exception it should see.

    The fix needs a mark on the raised value that script cannot forge. That
    is the actual design question in this work, and it is what makes it one
    piece rather than two: 01a074ce-ff7d changes what traps ARE, and this
    issue needs something to test for. Doing either alone means doing it
    twice.

    ## Why it is worth more than its severity suggests

    It silently weakens tests. The spec suite's own delegate-correct-targets
    (`external/wasm-testsuite/tests/legacy/try_delegate.wast:100`) puts
    `catch_all unreachable` on every handler a delegation must skip, so that
    landing on the wrong one traps and is observable. Here the trap is caught
    and the function answers 1 either way -- it passed both before and after
    the delegate fix (commit "Wasm: delegate ignored its depth"). That is why
    test/wasm/e2e-try-delegate.wat carries delegate-targets-obs beside it.
    Any other test resting on a trap being observable is equally inert, and
    nothing announces it.
