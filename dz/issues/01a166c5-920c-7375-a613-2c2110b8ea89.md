Wasm memory access reaches bytecode as untyped property access. Nothing in
the bytecode says that the object is a typed-array view or that the index is
a number, so the JIT compiles every load and store site for a JS array. That
code can never run for Wasm, and it makes up about half of all JIT'd Wasm
code. This is a fix in the Wasm frontend and the bytecode, not a JIT
heuristic.

Sibling: 01a166c5-9233 (i32 shifts, bitwise ops and `===` have no typed bytecode).
Umbrella: 01a0684a-6a8f (typed IR for wasm-competitive codegen), item 2.
Measurements: hermes-node dz 01a14270-48bc, section "Where the code size
comes from".

## Today's lowering

`WasmIRGen::onLoad` / `onStore` (lib/WasmIRGen/WasmIRGen.cpp:6997, :7383)
lower an aligned access to:

- `addr >>> log2(width)` to get an element index;
- the typed-array view (HEAP32 etc.) via `loadMemView`, which is a
  `LoadFromEnvironment`;
- `LoadPropertyInst` / `StorePropertyStrictInst` on that view, which become
  `GetByVal` / `PutByValStrict`;
- for a load only: `=== undefined` and a `CondBranch` to a block calling
  `helpers_.emitTrap()` (`CallBuiltin HermesBuiltin.wasmTrap`). The i64.load32
  aligned path at :7213-7230 is one instance.

Repro (ASan build of wasm-new at b3d30e4f7):

    (module
      (memory (export "mem") 1)
      (func (export "ld") (param i32) (result i32) (i32.load (local.get 0)))
      (func (export "st") (param i32 i32) (i32.store (local.get 0) (local.get 1))))

`wat2wasm mem.wat -o mem.wasm && hermesc -wasm -O -dump-bytecode mem.wasm`:

A store has no check. `emitMemoryBoundsCheck` (:6976) runs only under
`-test262`, so in a normal build an out-of-bounds store is silently dropped
(a typed-array store past the end is a no-op), while the same out-of-bounds
load traps. Verified with the module above: `st(65536, 42)` returns normally
and `ld(65536)` throws. doc/WasmSpecTestStatus.md records this as deliberate,
pending "new instructions and a real bounds-checked access path". This issue
is that path.

Module-wide in parser.wasm, 77% of all `JStrictEqual`s are these OOB checks
and 94% of all `CallBuiltin`s are `wasmTrap`.

## Why it is expensive

Measured by the hermes-node session on Linux x86-64 Release, at the
hermes-node gitlink, on hermes-parser's 768,303-byte parser.wasm:

- every compiled version dumped with `-Xdump-jitcode=1`;
- each listing reassembled with llvm-mc;
- every byte attributed to the bytecode op, inline tier, register sync or
  slow path that emitted it.

Totals land 7.5% under the JIT's own figures, because llvm-mc picks short
jumps where asmjit uses long ones. The shares are unaffected.

All Wasm functions, version 1: 105,959 bytecode instructions -> 11.0 MB of
x86, 104 bytes per instruction.

| op | % of instructions | % of bytes | bytes each |
| --- | --- | --- | --- |
| PutByValStrict | 11.6% | 38.6% | 347 |
| GetByVal | 7.8% | 13.1% | 175 |
| JStrictEqual + its slow path | 6.8% | 12.2% | ~188 |
| AddN (for contrast) | 15.3% | 2.6% | 18 |
| Mov (for contrast) | 12.7% | 1.2% | 10 |

- PutByValStrict's 347 bytes are 160 for the inline fast JS-array store, 178
  for the GC write barrier ("store with barrier predicate"), and sync.
- GetByVal's 175 bytes are mostly a 152-byte inline fast JS-array load.
- Register syncs are only 4.8% of all bytes. The size does not come from
  syncs.

With no type information, the JIT inlines the JS-array tiers at each site:
the cell-kind test `cmp byte ptr [rdx+4],0x1E` (JSArray), a double-to-int
index conversion with an exactness check, a bounds check, an empty-slot
check, and for stores the write barrier. A typed array fails the 0x1E test
on every execution and falls through to an indirect call to
`_jit_put_by_val_strict` / `_jit_get_by_val`. So about 60 of the ~75 x86
instructions per store site are dead code for Wasm.

Recompiles make sites bigger, not smaller. They put a typed-array tier
(kind 0x27) in front and keep the JS-array tier and the barrier. In version
3 of wasm_func_128 only 8 of 2,186 store sites and 14 of 1,128 load sites
had the typed-array tier, because almost nothing had executed by then.

Worst functions, per version:

- wasm_func_128: 1.65 MB (1.79 MB by the JIT's count), 14,258 instructions,
  116 B/inst; 59% of its bytes are typed-array access (2,186 stores, 1,128
  loads);
- wasm_func_103: 1.11 MB, 58% typed-array access;
- wasm_func_151: 0.85 MB, 63%;
- wasm_func_315: 131 B/inst, 74%.

Cost per site: about 600 bytes of x86 per load (7 bytecode instructions) and
about 500 per store, against roughly one mov plus a bounds check in a native
compiler. Typed-array GetByVal + PutByValStrict alone are 51.7% of all JIT'd
Wasm bytes; the OOB `=== undefined` and trap tail add about 12% more.

## The information exists and is dropped

The IR already marks the index as a Number (`idx->setType(Type::createNumber())`
at every site), and the view is always a typed array of a kind fixed by the
opcode. Both are lost when the bytecode is emitted, because the bytecode has
no typed-array load/store instruction to carry them.

## Direction

- Give Wasm memory access typed opcodes: Load/Store {I8, U8, I16, U16, I32,
  F32, F64} on a typed-array view with an int32 index. At the very least,
  give the bytecode a way to say that a ByVal site is a typed array of a
  known element kind.
- Then the interpreter, the JIT and SH codegen all emit a direct element
  access, and the JIT never emits JS-array tiers or a write barrier for them.
  Typed-array elements are not GC pointers.
- Fold the OOB check into the opcode: it traps itself, instead of returning
  undefined for `=== undefined` + `CallBuiltin wasmTrap` to test. That also
  makes stores trap out of bounds outside `-test262`, closing the silent-drop
  gap above.
- Worth weighing: an opcode that takes the byte address instead of an
  element index drops the `>>> log2(width)` shift entirely. On hosts that
  allow unaligned access, it would also make a misaligned access correct
  without the byte-assembly path. That path is another `-test262`-only
  behavior recorded in doc/WasmSpecTestStatus.md.

## Versioning

- This changes the bytecode produced from identical input, so
  `WASM_CODEGEN_VERSION` (include/hermes/WasmFrontend/WasmCodegenVersion.h)
  must be bumped. That header comes from the wasm-module-cache branch and is
  not on wasm-new yet. Bump it wherever the header exists when this lands.
- New opcodes are a bytecode format change. That is covered by the
  release-time BYTECODE_VERSION bump, not a per-change one.
